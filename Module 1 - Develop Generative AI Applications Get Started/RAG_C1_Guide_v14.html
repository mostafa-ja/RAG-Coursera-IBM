⭐ The 12 core ideas of Course 1, in plain words

Almost every app in this course follows one pattern: template → chat model → parser, then serve it. Ideas 1–8 make that pattern work well, ideas 9–11 extend it (your own data, conversation, tools), and idea 12 ships it. If you can explain each row in your own words, you are ready for the quizzes and for your first project.

IdeaWhat it really isUse it in a project when…Lesson
1. Prompt = 4 elementsA prompt is a mini-spec: instructions (what to do), context (background), input data (the text to process) and an output indicator (where and how to answer).Every LLM call. A missing element is the most common cause of vague answers.1.4
2. In-context learningThe model learns the task from examples inside the prompt (zero-, one-, few-shot). No training, and nothing is saved after the call.Start zero-shot; add 2–5 examples when the labels or format drift.1.5, 1.6
3. Chain-of-thought & self-consistencyCoT: ask for the steps before the answer. Self-consistency: ask several times and keep the majority answer.Multi-step maths or logic, or a field where one wrong answer is costly.1.6
4. Generation parametersKnobs for how the next token is picked: temperature, top_p, top_k = how random; max_tokens = length cap.Low temperature (0–0.3) for extraction and JSON; higher (0.7–1) for creative text.1.10
5. Chat model + messagesThe model reads a list of role-tagged messages: System (rules), Human (user), AI (earlier answers).Put fixed rules in the System message; send the history as messages.2.2
6. Prompt templatesA reusable prompt with {placeholders} that are filled at run time.One template per task; never glue prompts together with string concatenation.1.7, 2.3
7. LCEL & Runnablesprompt | llm | parser: each step's output is the next step's input. Every step has invoke, batch and stream.The backbone of every app in this course and in the RAG courses.1.8
8. Output parsersTurn the model's text into Python data: str, list, dict or a Pydantic object.Whenever code, not a person, reads the answer (APIs, databases, UIs).2.4, 3.4
9. Documents → chunks → embeddings → retrieverSplit long text into chunks, turn each chunk into a vector, then fetch the chunks most similar to the question.The “R” in RAG: answering from your own files.2.5

Key takeaways

Common pitfalls
  • Forgetting the Notebook access toggle in Secrets → SecretNotFoundError.
  • Restarting the runtime clears variables, so re-run the setup cell first.
  • Mixing .invoke() results: chat models return an AIMessage. Use .text (always a str; Gemini 3 .content can be a list of blocks) or add StrOutputParser().
  • Tiny max_output_tokens + a thinking model = empty reply. Leave headroom (1024) or use thinking_level="low".
  • Hitting free-tier rate limits in loops. Add time.sleep(2) or use gemini-3.5-flash-lite.
Remember
  • Swap the model, keep the chain. This idea (model-agnostic components) is LangChain's core benefit, modularity.

AI landscape: from rules to generative models

⏱ ~4 min🧭 2 diagrams💻 0 code cells🧠 3 recall Qs
In a nutshellDiscriminative AI draws boundaries between classes. Generative AI learns the data distribution and creates new content. Foundation models (LLMs such as GPT, PaLM/Gemini, Llama) are big pre-trained generative models that you adapt to many tasks.
🎯 After this lesson you can
  • Tell discriminative AI (classify) from generative AI (create).
  • Name the 4 model families behind GenAI: GANs, VAEs, transformers, diffusion.
  • Explain what a foundation model is and why it suits many tasks with little labelled data.
💡 In plain words

A discriminative model is an art critic who labels paintings; a generative model is a painter who makes new ones.

Foundation model

A large model pre-trained on broad, mostly unlabeled data that can be adapted to many downstream tasks via prompting or (light) tuning — ideal when you have many NLP tasks and little labeled data. Generative model families: VAEs, GANs, transformers (LLMs), diffusion models.

📽️ From the slide deck: evolution, building blocks, examples & tools

Generative AI models capture the underlying distribution of the training data and generate novel data points; discriminative AI distinguishes between classes of labelled data via a decision boundary but cannot understand context and cannot generate new content. Slide example: discriminative = “Is this image a drawing of a nest on an egg?”; generative = “Draw an image of a nest with three eggs in it.” (Harvard Business Review: AI can not only boost analytic and decision-making abilities but also heighten creativity.)

Key takeaways

Why it matters
  • Picking the wrong family wastes effort: predicting churn from history is ML; writing the retention email is GenAI.
  • Foundation models let one pre-trained model serve many tasks with little labelled data — the premise of this whole certificate.
Common pitfalls
  • Calling every AI system “generative”. Classifiers and recommenders are discriminative.
  • Assuming generative = unsupervised only. GenAI models are pre-trained on unlabelled data and then often fine-tuned with labels.
Remember
  • Discriminative learns P(y|x), a boundary. Generative learns P(x), the data itself.

NLP: NLU and NLG

⏱ ~2 min🧭 1 diagram💻 0 code cells🧠 2 recall Qs
In a nutshellNLP has two directions. NLU turns unstructured language into structured meaning. NLG turns structured data or intent back into fluent text. LLMs do both.
🎯 After this lesson you can
  • Define NLU (text → meaning) and NLG (meaning → text).
  • Spot which half a real application uses.
  • Use an LLM to do both: extract structured data, then write a reply.
💡 In plain words

NLU is reading a letter and noting who, what, when; NLG is writing the reply.

⬅ Builds on 1.1 AI landscape: from rules to generative models
➡ Leads to 1.3 Core GenAI terminology (Comprehensive Guide)

  • NLU (Natural Language Understanding): unstructured text → structured meaning (intent, entities, sentiment). Sub-tasks: tokenization, NER, parsing.
  • NLG (Natural Language Generation): structured data → human-readable text.
  • Applications: translation, sentiment analysis, chatbots/virtual assistants, summarisation, speech recognition.

💻 Try it in Colab: NLU then NLG with one LLM

# Uses llm from the 2-cell Gemini init (section 0.2) — gemini-3.8-flash
precise = ChatGoogleGenerativeAI(model="gemini-3.8-flash", temperature=0)   # T=0 → repeatable extraction

text = "Hi, I'm Sara. My order #4512 arrived broken yesterday in Berlin. I want a refund."

# NLU: unstructured text -> structured meaning
nlu = precise.invoke(
    "Extract intent, sentiment, and entities (name, order_id, city) from the text. "
    "Return only JSON.\nText: " + text).text
print("NLU ->", nlu)

# NLG: structured data -> natural language
nlg = precise.invoke("Write a short, polite support reply based on this JSON:\n" + nlu).text
print("NLG ->", nlg)

First basic prompt (slide): the input The wind is → the model continues “Blowing gently through the trees, whispering secrets and stories to anyone who cares to listen.” With no instructions or output indicator, the model simply continues the text. Add elements to steer it.

from langchain_core.prompts import PromptTemplate
from langchain_google_genai import ChatGoogleGenerativeAI
llm = ChatGoogleGenerativeAI(model="gemini-3.8-flash", temperature=0)

four_part = PromptTemplate.from_template(
    "{instruction}\n"            # 1. instructions
    "Context: {context}\n"       # 2. context
    "Review: {review}\n"         # 3. input data
    "Sentiment:")                # 4. output indicator

prompt = four_part.format(
    instruction="Classify the following customer review into neutral, negative, or positive sentiment.",
    context="This review is part of feedback for a recently launched product.",
    review="The product arrived late, but the quality exceeded my expectations.")
print(llm.invoke(prompt).text)    # e.g. "Positive"

# Compare: the bare prompt, with no elements
print(llm.invoke("The wind is").text)

🔍 Deeper look · From a good prompt to a reliable project prompt

A prompt that works once in a notebook is not yet a project prompt. In an app the same prompt runs on hundreds of different inputs, and your code must be able to read every answer. Four habits get you there:

HabitWhy it mattersIn the template
1 · Freeze everything except the dataInstructions, context and output format stay the same on every call; only the input changes. That is exactly what a prompt template is.Only {review} is a variable.
2 · Fence the input dataDelimiters show the model where the data starts and ends, so text inside a review (“ignore the above…”) is not read as an instruction.<review>{review}</review> or triple quotes
3 · Name the allowed answers“Sentiment:” alone allows “Positive.”, “mostly positive” or a whole paragraph. Your if statement needs one exact word.“Answer with one lowercase word.”
4 · Test on a small set, change one thing at a timePrompt engineering is this loop: run 5–10 varied inputs (mixed feelings, very short, another language), look at the failures, fix one element, run again.A Python list of test inputs
from langchain_core.output_parsers import StrOutputParser
sentiment = PromptTemplate.from_template(
    "Classify the customer review as positive, negative or neutral.\n"  # 1. instruction
    "The review is feedback on a recently launched product.\n"         # 2. context
    "<review>{review}</review>\n"                                      # 3. input data, fenced
    "Answer with one lowercase word.\nSentiment:")                     # 4. output indicator + allowed form
chain = sentiment | llm | StrOutputParser()

tests = ["Late, but great quality.", "Broke after one day.", "It is a phone.", "عالی بود"]  # last one: Persian "it was great"
for r in tests:
    ans = chain.invoke({"review": r}).strip()
    print(f"{r!r:32} → {ans}", "✅" if ans in {"positive", "negative", "neutral"} else "❌ fix the prompt")

Rule of thumb: if you cannot check the answer with one line of Python, the prompt is not finished yet.

Demonstrations of the task are provided in the prompt; the model adapts at inference time without updating weights.

🔍 Deeper look · Why few-shot works: the model continues a pattern

The model does not "study" your examples. It reads the whole prompt as one text and predicts what comes next. The examples make one continuation much more likely.

Statement: 'I just won my first marathon!' Emotion: Joy Statement: 'I can't believe I lost my keys again.' Emotion: Frustration Statement: 'My best friend is moving to another country.' Emotion: Sadness Statement: 'That movie was so scary I had to cover my eyes.' Emotion: ▮ ← most likely next word: an emotion, one word → "Fear"
  1. Format: every example is "Statement → Emotion: one word", so the answer copies this shape.
  2. Label style: Joy, Frustration, Sadness are short emotion names, so the model picks a similar name.
  3. Position: the prompt stops exactly where a label should come.

⭐ Quiz fact: in-context learning changes no model weights. The "learning" lives only inside this one prompt and is gone after the call.

🔍 Deeper look · The dict step: RunnablePassthrough, .assign() and the RAG pattern

The problem. A RAG prompt needs two values, {context} and {question}, but the user types only the question. Something must turn that one string into the dict {"context": …, "question": …}. That is the job of the dict step: each key gets its own small runnable, and all of them receive the same input. (Inside a chain, a dict becomes a RunnableParallel.)

You writeWhat it does with the inputWhat comes out
{"a": r1, "b": r2}

RunnablePassthrough()nothing; passes it on unchangedthe input itself
RunnablePassthrough.assign(c=r3)runs r3 on the input dictthe input dict plus key c (all old keys kept)

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda, RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser
from langchain_google_genai import ChatGoogleGenerativeAI

llm = ChatGoogleGenerativeAI(model="gemini-3.8-flash", temperature=0)

NOTES = ["Tender T-12 closes on 3 November 2026.",
         "The bid bond is 2% of the offer price."]
# pretend search: always returns both notes (in 2.5 this becomes vectorstore.as_retriever())
retriever = RunnableLambda(lambda question: NOTES)

def format_docs(docs):                       # list → one string for {context}
    return "\n".join(docs)

prompt = ChatPromptTemplate.from_template(
    "Answer only from the context. If the answer is not there, say: I don't know.\n"
    "Context:\n{context}\n\nQuestion: {question}")

rag = (
    {"context": retriever | format_docs,     # branch 1: question → notes → one string
     "question": RunnablePassthrough()}      # branch 2: the question, unchanged
    | prompt | llm | StrOutputParser()
)
print(rag.invoke("When does tender T-12 close?"))   # → 3 November 2026
print(rag.invoke("Who is the buyer?"))              # → I don't know (not in the notes)

Keep everything with .assign(). In a project you usually want the answer and its sources (to show them in the UI, or to check them). .assign() adds one key at a time and keeps the old keys, so nothing gets lost:

rag_src = (
    RunnablePassthrough.assign(docs=lambda d: retriever.invoke(d["question"]))  # {question} + docs
    .assign(context=lambda d: format_docs(d["docs"]))                           # + context
    .assign(answer=prompt | llm | StrOutputParser())                            # + answer
)
out = rag_src.invoke({"question": "When does tender T-12 close?"})
print(out["answer"])    # the answer
print(out["docs"])      # the notes it used → your "sources"

At the last step the prompt receives question, docs and context, but it uses only {context} and {question}. Extra keys are ignored.

Three mistakes → fixes

  • KeyError in a later step: a dict step returns only its own keys. Add the key back ("question": RunnablePassthrough()) or use .assign().
  • Wrong input type: RunnablePassthrough() passes on exactly what it gets. Call rag with a string; if you pass a dict, the real retriever in 2.5 receives a dict and fails. Call rag_src with a dict, because it reads d["question"].
  • A Python list printed inside {context}: a retriever returns a list of documents, but the prompt needs one string. Keep | format_docs (with real documents: "\n\n".join(d.page_content for d in docs)).

Why it matters: this is the shape of every RAG chain in Course 2. Only the pretend retriever changes, to vectorstore.as_retriever(). See 2.5 and the mini RAG with sources in P8.

🔍 Deeper look · What temperature really does, and which settings to use in a project

Temperature in numbers. Say the model scores three next words: blowing = 2, strong = 1, cold = 0. The scores are divided by the temperature and then turned into probabilities (softmax):

TemperatureblowingstrongcoldEffect
0.5 (low)87%12%2%The favourite almost always wins → focused, repeatable.
1.0 (neutral)67%24%9%The model's own odds.
2.0 (high)51%31%19%Odds flatten → more surprising words, more mistakes.

Temperature 0 is the limit case: always take the top word (greedy). top_k and top_p run after this step and only remove unlikely words, so in practice temperature is the one knob you tune. Leave top_k/top_p at their defaults unless you have a reason.

Starting presets for project tasks

TasktemperatureWhy
Classification, extraction, JSON output0Same input → same answer, and code can parse it.
Answering from your documents (RAG)0–0.3Stays close to the given context; fewer invented details.

Key takeaways

Why it matters
  • Same prompt, different settings → different reliability. Extraction/classification needs low temperature; brainstorming needs higher.
  • Parameters are cheaper than fine-tuning for steering style.
Pitfalls
  • Setting temperature high and top_p=1 for JSON output → broken JSON.
  • max_new_tokens too small → truncated answers that look like "model errors".
  • Thinking top_k=1 and temperature=0 are different "modes" — both make the output (almost) deterministic.
Remember
  • Low T (0–0.3) = precise · High T (0.7–1.2) = creative.
  • top_p 0.2 = very strict nucleus; 0.9 = loose.

🔍 Deeper look · What goes into a chat model, and what comes out

A chat model does not take one string. It takes a list of messages. Each message has a role and some content. The model answers with one new message: an AIMessage.

msg = llama_llm.invoke( ← llama_llm is a ChatGoogleGenerativeAI object in Colab [ SystemMessage(content="You are a helpful AI bot that assists a user in choosing the perfect book to read in one short sentence"), ← rules for the whole chat HumanMessage(content="I enjoy mystery novels, what should I read?") ← the user's turn ] ) type(msg) → AIMessage ← the model's turn msg.text → one short sentence (str) ← always a plain str: use this msg.content → may be a list of blocks ← Gemini 3 can return parts, so .content is not always a str reply.content → may be a list of blocks ← Gemini 3 can return parts, so .content is not always a str

The notebook's fitness example adds an earlier AIMessage(content="You should try a CrossFit class") before the next HumanMessage: that is how the model "remembers" the chat.

  1. System = instructions and role. It is sent first and shapes every answer.
  2. Human = what the user says. AI = what the model said before (used for chat history).
  3. To continue a chat, append the AIMessage and the next HumanMessage to the same list and call invoke again. The model has no memory of its own: the list is the memory.

⭐ Quiz fact: an LLM takes text in and gives text out; a chat model takes messages in and gives an AIMessage out.

from langchain_core.prompts import PromptTemplate, FewShotPromptTemplate
from langchain_community.example_selectors import NGramOverlapExampleSelector

example_prompt = PromptTemplate.from_template("Input: {input}\nOutput: {output}")

            {"input": "pilot",  "output": "plane"},
            {"input": "driver", "output": "car"}]

selector = NGramOverlapExampleSelector(
    examples=examples, example_prompt=example_prompt,
    threshold=-0.1,   # -0.1 = keep all, sorted by overlap; 0.0 = drop zero-overlap; >1 = none
)
dynamic_prompt = FewShotPromptTemplate(
    example_selector=selector, example_prompt=example_prompt,
    prefix="Give the location an item is usually found in",
    suffix="Input: {item}\nOutput:", input_variables=["item"],
)
print(dynamic_prompt.format(item="plant"))   # then: (dynamic_prompt | llm).invoke({"item": "plant"})
🔍 Deeper look · How a similarity example selector picks the shots

A few-shot prompt has room for only a few examples. An example selector chooses which examples to show for the current input. The semantic-similarity selector works like a tiny search engine:

  1. Every stored example is turned into an embedding (a list of numbers that captures meaning) and saved in a vector store.
  2. The new input is embedded the same way.
  3. The selector returns the k examples whose embeddings are closest to the input.
Input: "My flight was cancelled and nobody helped me." k = 2 example similarity (illustrative) "The hotel lost my booking." → angry 0.82 ✔ picked "The train was late again." → annoyed 0.77 ✔ picked "I love this new phone!" → happy 0.21 "What time does the shop open?" → neutral 0.15

The prompt now shows two complaint examples, so the model copies the right style for a complaint. Other selectors use other rules: MMR = similar and different from each other (diversity), n-gram overlap = shared words, length-based = as many examples as fit a length limit.

from pydantic import BaseModel, Field

🔍 Deeper look · A parser's two jobs, and what to do when parsing fails

The model can only ever return text. A parser is the bridge between that text and your Python code, and it works at two moments:

  1. Before the call (writes): parser.get_format_instructions() produces a paragraph such as “Return a JSON object with the keys…”. You put it in the prompt, usually through partial_variables.
  2. The call: the model replies with an AIMessage. This is still just text, possibly wrapped in ```json fences or with an extra sentence.
  3. After the call (reads): the parser removes the fences, converts the text (json.loads, split on commas…) and, for Pydantic, checks the field types. You get a Python object, or an OutputParserException.

try:
    r = chain.invoke({"review": "Late, but great quality."})
    print(r.sentiment, "|", r.reason)                       # attributes, not dict keys
except (OutputParserException, ValueError) as e:
    print("Could not parse, use a default or retry:", e)

Rule of thumb: use StrOutputParser when a person reads the answer and a Pydantic schema when code reads it.

Key takeaways

Why it matters
  • Apps need data (dicts, lists, objects), not prose. Parsers turn an LLM into a function with a predictable return type.
  • Many providers also support llm.with_structured_output(MyModel), which uses native JSON/tool calling. It is often more reliable than prompt-only parsing.
Pitfalls
  • Forgetting format_instructions → model returns prose, JSON parse fails.
  • CSV output from an LLM → CommaSeparatedListOutputParser (not JSON/XML/“PandaDataFrameParser”).
  • Markdown code fences around JSON: JsonOutputParser handles them; json.loads does not.
Remember
  • CSV list → CommaSeparatedListOutputParser · JSON → JsonOutputParser · typed object → PydanticOutputParser · plain text → StrOutputParser.

               metadata={"my_document_id": 234234, "my_document_source": "About Python"})

                                          separators=["\n\n", "\n", ". ", " ", ""])

# CharacterTextSplitter(chunk_size=200, chunk_overlap=20, separator="\n") splits on ONE separator

emb = GoogleGenerativeAIEmbeddings(model="models/gemini-embedding-2")  # replaces WatsonxEmbeddings (slate-125m)
# = the `embeddings` object from Cell 2. Optional: task_type="RETRIEVAL_DOCUMENT" (docs) / "RETRIEVAL_QUERY" (questions)
# — langchain-google-genai already uses these two task types by default.
print(len(emb.embed_query("How are you?")))      # vector dimension

vs = Chroma.from_documents(chunks[:100], emb)   # free tier: ≤100 texts per embedding call
print(vs.similarity_search("What is attention?", k=3)[0].page_content[:200])

retriever = vs.as_retriever(search_kwargs={"k": 3})       # vector-store-backed retriever
print(retriever.invoke("multi-head attention"))

# Modern memory: RunnableWithMessageHistory + InMemoryChatMessageHistory (Colab-ready)
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory

    ("system", "You are a friendly assistant. Keep answers short."),
    MessagesPlaceholder("history"),          # <- memory is READ here
    ("human", "{input}"),
])
store = {}                                   # session_id -> history
def get_history(session_id):
    return store.setdefault(session_id, InMemoryChatMessageHistory())

chat = RunnableWithMessageHistory(prompt | llm, get_history,
                                  input_messages_key="input", history_messages_key="history")

🔍 Deeper look · What ConversationBufferMemory really sends

The model itself remembers nothing. "Memory" means: send the old turns again with every new question. On the third call, ConversationChain sends roughly this text:

The following is a friendly conversation between a human and an AI. … Current conversation: Human: Hello, I am a little cat. Who are you? AI: (reply 1) Human: What can you do? AI: (reply 2) Human: Who am I?. AI: ▮
  • The answer "a little cat" comes from line 3 of the history, not from the model's memory.
  • The history grows every turn, so each call costs more tokens. Long chats need a shorter history (only the last turns, or a summary).

  • Give tools a clear name and description.

💡 In plain words

A chain follows a recipe; an agent is a cook who looks at the fridge (tools) and decides what to do next.

⬅ Builds on 2.6 Memory & chains
➡ Leads to 3.1 How an LLM works (lab primer)

Agents are dynamic systems where the language model determines the sequence of actions, integrating with tools (search engines, databases, websites, calculators). Example: “population of Italy?” → the LLM picks a tool (DB lookup / search), calls it, and answers with the result.

# ── Tools & agents (ReAct) ────────────────────────────────────────────────
from langchain_core.tools import Tool
from langchain_classic.tools import tool
from langchain_experimental.utilities import PythonREPL
from langchain_classic.agents import create_react_agent, AgentExecutor

python_repl = PythonREPL()
python_calculator = Tool(name="Python Calculator", func=python_repl.run,
    description="Useful for math. Input must be valid python; print the result.")

@tool
def search_weather(location: str) -> str:
    """Search for the current weather in the specified location."""
    return f"The weather in {location} is currently sunny and 72°F."   # stub

tools = [python_calculator, search_weather]
react_prompt = PromptTemplate.from_template("""Answer the following questions as best you can.
You have access to the following tools:
{tools}
Use the following format:
Question: the input question you must answer
Thought: you should always think about what to do
Action: the action to take, should be one of [{tool_names}]
Action Input: the input to the action
Observation: the result of the action
... (this Thought/Action/Action Input/Observation can repeat N times)
Thought: I now know the final answer
Final Answer: the final answer to the original input question
Begin!
Question: {input}
Thought:{agent_scratchpad}""")

agent = create_react_agent(llm=llm, tools=tools, prompt=react_prompt)
agent_executor = AgentExecutor(agent=agent, tools=tools, verbose=True,
                               handle_parsing_errors=True, max_iterations=5)
print(agent_executor.invoke({"input": "What is the square root of 256 and the weather in Paris?"})["output"])

Tools vs toolkits

A tool is one callable (name + description + function) the agent may choose, e.g. a calculator or Wikipedia search. A toolkit is a bundle of related tools for one integration (e.g. SQL database toolkit, file-management toolkit, Gmail toolkit). Built-ins load with load_tools(["wikipedia", "llm-math"], llm=llm) (from langchain_community.agent_toolkits.load_tools), custom ones with the @tool decorator. The tool description is what the LLM reads to decide — write it like documentation.

How an LLM works (lab primer)

⏱ ~3 min🧭 1 diagram💻 2 code cells🧠 2 recall Qs
In a nutshellAn LLM is a next-token predictor: tokens → embeddings → attention → stacked transformer layers → probabilities → sample one token → repeat. Training at massive scale makes the predictions useful.
🎯 After this lesson you can
  • Explain tokenization, embeddings, attention, transformer layers and next-token prediction.
  • Describe training vs inference.
💡 In plain words

Autocomplete on a huge scale: predict the next token, again and again, using everything said so far.

⬅ Builds on 2.7 Agents & tools
➡ Leads to 3.2 Choosing the right model

  • Tokenization: text → tokens (Byte Pair Encoding merges common letter pairs; rare words split); each token gets a unique ID.
  • Embeddings: IDs → vectors of hundreds of numbers; similar meanings cluster (“cat” near “dog”, far from “airplane”).
  • Attention (“Attention is All You Need”): each token looks at every other token; multi-head attention heads specialise in parallel (“sat” ↔ “cat”).
  • Transformer layers: dozens stacked; early = grammar, deep = reasoning/facts; residual connections pass each layer's input forward for stability.
  • Next-token prediction: the training objective (“The capital of France is” → “Paris”).
  • Massive-scale training: trillions of words, thousands of GPUs for months, billions of parameters adjusted via backpropagation.
  • Inference: generate token by token, feeding each back in (autoregressive); temperature & sampling trade creativity vs predictability.

Next-token probabilities & temperature — see it with numbers

import numpy as np
tokens = ["Paris", "Lyon", "London", "banana"]
logits = np.array([6.0, 3.5, 3.0, 0.5])            # raw scores from the final layer
def softmax(z, T=1.0):
    z = z / T; e = np.exp(z - z.max()); return e / e.sum()
for T in (0.2, 1.0, 2.0):                           # low T = sharper (≈ greedy), high T = flatter (creative)
    print(f"T={T}:", dict(zip(tokens, softmax(logits, T).round(3))))
# greedy decoding = argmax; sampling = np.random.choice(tokens, p=softmax(logits, T))

🔍 Deeper look · Six facts about next-token prediction that shape every app you build

“An LLM predicts the next token, one at a time, from everything before it.” Almost every design rule in this course follows from that one sentence:

FactWhat it means in your appWhat you do
1 · It works in tokensYou pay per token, and the context window limits input + output together. One English word ≈ 1.3 tokens; Persian and other non-Latin scripts often need more.Keep prompts lean; check usage_metadata.
2 · It only sees the current promptNothing is remembered between two calls.Send the earlier messages again: that is “memory” (2.6).
3 · It predicts likely text, it doesn't look facts upA fluent but wrong answer (hallucination) is a normal output, not a bug.Put the facts in the prompt: that is RAG (2.5, Part D).
4 · Every token is conditioned on what came beforeWording, order and examples in the prompt change the result.Clear instructions, fenced data, output indicator at the end (1.4).
5 · The next token is sampledThe same prompt can give different answers.Temperature 0 when code reads the answer (1.10).
6 · Output is produced token by tokenLong answers are slow; the first words are ready long before the last.Ask for short answers; use .stream() in chat UIs.

Rule of thumb: when an app misbehaves, ask which of the six facts you forgot. The usual answers are 2 (no memory), 3 (no facts in the prompt) or 5 (temperature too high).

from pydantic import BaseModel, Field
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import JsonOutputParser
from langchain_google_genai import ChatGoogleGenerativeAI
from config import PARAMETERS, LLAMA3_MODEL_ID, GRANITE_MODEL_ID, MIXTRAL_MODEL_ID

class AIResponse(BaseModel):                       # the JSON contract the UI relies on
    summary: str = Field(description="Summary of the user's message")
    sentiment: int = Field(description="Sentiment score from 0 (negative) to 100 (positive)")
    response: str = Field(description="Suggested response to the user")

json_parser = JsonOutputParser(pydantic_object=AIResponse)

def initialize_model(model_id):                    # ChatWatsonx → ChatGoogleGenerativeAI
    return ChatGoogleGenerativeAI(model=model_id, **PARAMETERS)

llama3_llm, granite_llm, mixtral_llm = map(initialize_model, [LLAMA3_MODEL_ID, GRANITE_MODEL_ID, MIXTRAL_MODEL_ID])

V = ["system_prompt", "format_prompt", "user_prompt"]
llama3_template = PromptTemplate(input_variables=V, template=
  "<|begin_of_text|><|start_header_id|>system<|end_header_id|>\n{system_prompt}\n{format_prompt}<|eot_id|>"
  "<|start_header_id|>user<|end_header_id|>\n{user_prompt}<|eot_id|><|start_header_id|>assistant<|end_header_id|>\n")
granite_template = PromptTemplate(input_variables=V, template=
  "System: {system_prompt}\n{format_prompt}\nHuman: {user_prompt}\nAI:")
mixtral_template = PromptTemplate(input_variables=V, template=
  "<s>[INST]{system_prompt}\n{format_prompt}\n{user_prompt}[/INST]")

def get_ai_response(model, template, system_prompt, user_prompt):
    chain = template | model | json_parser                         # LCEL
    return chain.invoke({"system_prompt": system_prompt, "user_prompt": user_prompt,
                         "format_prompt": json_parser.get_format_instructions()})

def llama3_response(s, u):  return get_ai_response(llama3_llm,  llama3_template,  s, u)

def mixtral_response(s, u): return get_ai_response(mixtral_llm, mixtral_template, s, u)
🔍 Deeper look · From format instructions to a Python dict
  1. json_parser.get_format_instructions() turns AIResponse (summary · sentiment · response) into text that describes the JSON shape.
  2. The template puts this text into {format_prompt}, next to {system_prompt} and {user_prompt}.
  3. The model answers with JSON text, for example {"summary": "Late, damaged delivery", "sentiment": 15, "response": "We are sorry…"}.
  4. JsonOutputParser turns that text into a Python dict.
  5. app.py adds duration and returns it with jsonify(result); the page shows data.response.

⚠ JsonOutputParser(pydantic_object=…) uses the class to write the instructions; it does not strictly check the types. If you need strict checking, validate the dict yourself (e.g. AIResponse(**result)).

from flask import Flask, request, jsonify, render_template
from model import llama3_response, granite_response, mixtral_response
import time
app = Flask(__name__)

@app.route("/", methods=["GET"])
def index():
    return render_template("index.html")           # templates/index.html (chat UI + JS fetch)

@app.route("/generate", methods=["POST"])
def generate():
    data = request.json
    user_message, model = data.get("message"), data.get("model")
    if not user_message or not model:
        return jsonify({"error": "Missing message or model selection"}), 400
    system_prompt = "You are an AI assistant helping with customer inquiries. Provide a helpful and concise response."
    start = time.time()
    try:
        fn = {"llama3": llama3_response, "granite": granite_response, "mixtral": mixtral_response}.get(model)
        if fn is None:
            return jsonify({"error": "Invalid model selection"}), 400
        result = fn(system_prompt, user_message)
        result["duration"] = time.time() - start   # measure speed per model
        return jsonify(result)
    except Exception as e:
        return jsonify({"error": str(e)}), 500

🔍 Deeper look · One request, end to end (and how to find where it broke)

Clicking Submit sets off 7 steps, always in the same order. If you know the order, you can find any bug quickly: the error tells you which step failed.

#What happensCode that does itIf it fails you see
1The page's JavaScript sends the message + model as JSONfetch('/generate', {method:'POST', body: JSON.stringify(…)}) in index.htmlNothing happens / network error → server not running, wrong port
2Flask matches URL + method to a function@app.route("/generate", methods=["POST"])404 wrong URL · 405 GET instead of POST
3The route reads and checks the inputdata = request.json, data.get("message")400 “Missing message or model selection”
4The route picks the model function{"llama3": llama3_response, …}.get(model)400 “Invalid model selection”
5The chain runs: template → model → parsertemplate | model | json_parser in model.py500 + error text: API key, quota (429 / RESOURCE_EXHAUSTED), bad JSON

The status code tells you where to look: 404/405 → the route · 400 → the request you sent · 500 → the chain or the model (read the error text).

Three layers, one contract. index.html (UI) only knows the JSON keys. app.py (API) only does HTTP and checks input. model.py (logic) holds the prompts, models and parser. The contract between them is the set of keys in AIResponse. To add a field, you change AIResponse and the UI; app.py stays the same.

P1 · Project starter cell: config + model factory

⏱ ~3 min💻 1 code cell🧩 skills 1, 7📖 learn first: 0.2, 1.10, 2.2
In a nutshellPut every setting (model names, temperatures, limits) in one config dict and create models through one factory function. Swapping Gemini models, or later a provider, becomes a one-line change.
🎯 Use it when
  • You start any new notebook or project.
  • You need several models with different settings (precise extractor + creative writer).
💡 In plain words

A light switch panel: all the knobs in one place, labelled, instead of wires hidden in every room.

from google.colab import userdata                      # 🔑 Secrets panel → GOOGLE_API_KEY → Notebook access ON
from langchain_google_genai import ChatGoogleGenerativeAI, GoogleGenerativeAIEmbeddings

os.environ["GOOGLE_API_KEY"] = userdata.get("GOOGLE_API_KEY")   # never paste the key into code

CONFIG = {
    "chat_model":  "gemini-3.8-flash",       # main model used in the course notebooks
    "cheap_model": "gemini-3.5-flash-lite",  # fast/cheap model for simple steps or fallback
    "embed_model": "models/gemini-embedding-2",
    "presets": {                             # one preset per kind of task (skill 7)
        "precise":  {"temperature": 0.0, "max_output_tokens": 512},   # extraction, classification, JSON
        "balanced": {"temperature": 0.3, "max_output_tokens": 1024},  # Q&A, summaries, RAG answers
        "creative": {"temperature": 0.8, "max_output_tokens": 1024},  # brainstorming, marketing copy
    },
}

def make_llm(preset="balanced", model=None, **overrides):
    """Model factory: make_llm('precise'), make_llm('creative', model=CONFIG['cheap_model'])."""
    params = {**CONFIG["presets"][preset], **overrides}
    return ChatGoogleGenerativeAI(model=model or CONFIG["chat_model"], max_retries=2, **params)

llm        = make_llm("balanced")
extractor  = make_llm("precise")
writer     = make_llm("creative")
embeddings = GoogleGenerativeAIEmbeddings(model=CONFIG["embed_model"])

print(extractor.invoke("Reply with one word: ready?").text)

Key takeaways

Why it matters

  • Keeping the key in Secrets means you can share the notebook safely.
Common pitfalls

  • Using one temperature for everything: JSON extraction at 0.8 breaks parsers.
  • Forgetting to re-run the setup cell after a runtime restart → NameError: llm.

Toolkit · Pattern P2

P2 · The core loop: template → model → parser (invoke · batch · stream)

⏱ ~5 min💻 1 code cell🧩 skills 2, 3, 5, 6📖 learn first: 1.8, 2.3, 2.4
In a nutshell90% of GenAI code is prompt | llm | parser. Learn the three ways to run it: invoke (one input), batch (many inputs in parallel), stream (tokens as they arrive, for UIs). And always look at the final prompt before blaming the model.
🎯 Use it when
  • Any single-step task: summarise, classify, rewrite, translate, answer.
  • Processing a whole column of a DataFrame (batch).
  • Building a chat UI that shows text while it is generated (stream).
💡 In plain words

A coffee machine: the template is the recipe card, the model is the machine, the parser is the cup. invoke = one coffee, batch = a tray, stream = watching it pour.

# P2 · the core loop
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# 4 prompt elements (1.4): instruction + context in the system message, input data + output indicator in the human one
prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a support assistant for {product}. Answer in {language}. "
               "Be concise and never invent features."),                        # instruction + context
    ("human",  "Customer message:\n{message}\n\nReply in at most 3 sentences:"),  # input data + output indicator
])
chain = prompt | llm | StrOutputParser()

# 1) look at what the model will actually receive (debug habit #1)
print(prompt.invoke({"product": "SmartBottle", "language": "English", "message": "It leaks!"}).to_messages())

# 2) invoke — one input
print(chain.invoke({"product": "SmartBottle", "language": "English", "message": "It leaks!"}))

# 3) batch — many inputs, run concurrently (keep concurrency low on the free tier)
msgs = ["How do I charge it?", "Can I put it in the dishwasher?", "Where is my order?"]
inputs = [{"product": "SmartBottle", "language": "English", "message": m} for m in msgs]
for m, r in zip(msgs, chain.batch(inputs, config={"max_concurrency": 2})):
    print("Q:", m, "\nA:", r, "\n")

# 4) stream — print tokens as they arrive (what chat UIs do)
for chunk in chain.stream({"product": "SmartBottle", "language": "French", "message": "It leaks!"}):
    print(chunk, end="", flush=True)

# 5) fix some variables once, reuse the template (partial)
fr_support = prompt.partial(product="SmartBottle", language="French")
print((fr_support | llm | StrOutputParser()).invoke({"message": "Battery dies fast"}))

Key takeaways

Why it matters
  • A RAG chain is exactly this loop with one extra key ({context}) filled by a retriever.
  • batch is how you evaluate a prompt on 50 test questions in one cell.
Common pitfalls
  • KeyError / "missing variables": every {name} in the template needs a key in the input dict.
  • Literal braces in a template (e.g. a JSON example) must be doubled: {{"name": "..."}}.
  • Reading .content on Gemini 3: it can be a list of blocks. Use .text or StrOutputParser().
Remember
  • prompt | llm | StrOutputParser() · invoke / batch / stream · prompt.invoke(...) to see the real prompt.
🧠 Active recall: answer before you open
Your template contains Return JSON like {"label": "x"} and fails with a missing-variable error. Why?
The braces are read as a variable named "label": "x". Escape them as {{"label": "x"}}, or move the example into a variable / use get_format_instructions().
When do you use batch instead of a Python for loop over invoke?
When the inputs are independent: batch runs them concurrently (faster) and respects max_concurrency so you stay within rate limits.
Toolkit · Pattern P3

P3 · Reliable structured output (Pydantic) with validation & fallback

⏱ ~6 min💻 1 code cell🧩 skill 8📖 learn first: 2.4, 3.4
In a nutshellWhen code (not a human) reads the answer, ask for a schema, not prose. Define a Pydantic model → llm.with_structured_output(Model) returns a validated Python object. Keep JsonOutputParser + get_format_instructions() (the course method) as the portable fallback.
🎯 Use it when
  • Extracting fields (invoice, CV, ticket), classifying with fixed labels, returning JSON to a web front-end (3.4/3.5).
  • Later: generating search queries, grading retrieved documents, choosing the next agent step.
💡 In plain words

Instead of asking "tell me about this invoice", you hand the model a form with labelled boxes and it must fill every box.

# P3 · structured output
from typing import Literal, Optional
from pydantic import BaseModel, Field
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import JsonOutputParser

class Ticket(BaseModel):
    """A classified customer-support ticket."""
    category: Literal["billing", "technical", "shipping", "other"] = Field(description="main topic")
    urgency: int = Field(ge=1, le=5, description="1 = low, 5 = critical")
    summary: str = Field(description="one-sentence summary")
    order_id: Optional[str] = Field(default=None, description="order number if mentioned, else null")

prompt = ChatPromptTemplate.from_messages([
    ("system", "Classify the support message. Use only the information given."),
    ("human", "{message}"),
])

# A) modern way — schema-validated object (uses the model's native JSON/tool mode)
classifier = prompt | extractor.with_structured_output(Ticket, include_raw=True)
res = classifier.invoke({"message": "Order #A-991 never arrived and I'm travelling tomorrow!!"})
ticket = res["parsed"]                       # a Ticket instance (or None if parsing failed)
if res["parsing_error"]:
    print("⚠️ could not parse:", res["parsing_error"])
else:
    print(ticket.category, ticket.urgency, ticket.order_id)   # shipping 5 A-991
    print(ticket.model_dump())                                 # → dict, ready for jsonify / pandas

# B) course way (2.4 / 3.4) — format instructions in the prompt + JsonOutputParser
parser = JsonOutputParser(pydantic_object=Ticket)
prompt_b = ChatPromptTemplate.from_messages([
    ("system", "Classify the support message.\n{format_instructions}"),
    ("human", "{message}"),
]).partial(format_instructions=parser.get_format_instructions())
chain_b = prompt_b | extractor | parser                      # returns a plain dict
print(chain_b.invoke({"message": "I was charged twice this month."}))

# C) process a list safely: one bad item must not kill the whole run
msgs = ["App crashes on login", "Refund please", "asdfgh"]
for m, r in zip(msgs, classifier.batch([{"message": m} for m in msgs], return_exceptions=True)):
    print(m, "→", r if isinstance(r, Exception) else r["parsed"])

Key takeaways

Why it matters
  • Literal[...] turns free text into a fixed label set: the basis of routing (P5) and of RAG "relevance graders".
  • Field(description=…) is part of the prompt. Good descriptions = better extraction.
Common pitfalls
  • No Optional for fields that may be missing → the model invents values.
  • High temperature for extraction. Use the precise preset.
  • Parsing with json.loads on raw text with ```json fences around it. Use a parser.
Remember
  • Code reads it → schema. include_raw=True to inspect failures. return_exceptions=True for batches.
Toolkit · Pattern P4

P4 · Resilient calls: retries, fallbacks, rate limits, timeouts

⏱ ~4 min💻 1 code cell🧩 skill 14📖 learn first: 2.2, 3.2
In a nutshellFree-tier APIs fail: 429 rate limit, timeouts, overloaded models. Every Runnable has .with_retry() and .with_fallbacks(); chat models accept a rate_limiter. Three lines make a notebook survive a 100-question evaluation.
🎯 Use it when
  • Batch jobs, evaluations, ingestion of many chunks (embedding calls).
  • Anything a user will click on (the Flask app must not crash on one failed call).
💡 In plain words

Retry = ring again if nobody answers. Fallback = call a colleague if the boss is busy. Rate limiter = a queue at the door so you are not thrown out.

# P4 · resilience
from langchain_core.rate_limiters import InMemoryRateLimiter
from langchain_google_genai import ChatGoogleGenerativeAI

# 1) rate limiter: at most ~1 request every 4 s (adjust to your quota)
limiter = InMemoryRateLimiter(requests_per_second=0.25, check_every_n_seconds=0.1, max_bucket_size=1)
main  = ChatGoogleGenerativeAI(model=CONFIG["chat_model"],  temperature=0.2, rate_limiter=limiter, timeout=60)
cheap = ChatGoogleGenerativeAI(model=CONFIG["cheap_model"], temperature=0.2, timeout=60)

# 2) retry with exponential back-off, then 3) fall back to another model
robust_llm = main.with_retry(stop_after_attempt=3, wait_exponential_jitter=True).with_fallbacks([cheap])

chain = prompt | robust_llm | StrOutputParser()   # use exactly like a normal llm

# 4) never let one failure crash an app endpoint
def safe_answer(question: str) -> dict:
    try:
        return {"ok": True, "answer": chain.invoke({"product": "SmartBottle", "language": "English", "message": question})}
    except Exception as e:                          # log it, return a friendly message
        return {"ok": False, "error": type(e).__name__, "answer": "Sorry, the assistant is busy. Try again."}
print(safe_answer("Is it BPA-free?"))

Key takeaways

Why it matters
  • Embedding a 200-page PDF = hundreds of calls; without limits you hit 429 halfway and lose the run.
Common pitfalls
  • Calling .bind_tools() or .with_structured_output() on the retry wrapper fails. Do those first on the raw model, then wrap.
  • Retrying errors that will never succeed (invalid API key, bad request). Fix the cause instead.
Remember
  • model → .with_structured_output/.bind_tools → .with_retry → .with_fallbacks
Toolkit · Pattern P5

P5 · Multi-step pipelines: parallel, assign, route, vote

⏱ ~6 min💻 1 code cell🧩 skills 4, 6📖 learn first: 1.8, 1.6, 2.6
In a nutshellReal apps are several small LLM steps, not one giant prompt. LCEL gives you four shapes: sequence (|), fan-out (RunnableParallel), enrich (.assign keeps old keys and adds new ones), and route (a classifier decides which chain runs). Self-consistency is just "run 5×, vote".
🎯 Use it when
  • One input needs several outputs (summary + keywords + sentiment).
  • Different question types need different prompts (billing vs tech support).
  • An answer must be more reliable than one sample (math, logic).
💡 In plain words

A kitchen: parallel = three cooks on one order; assign = adding toppings without throwing away the pizza; route = the waiter sends drinks to the bar and food to the kitchen.

# P5 · pipeline shapes
from collections import Counter
from typing import Literal
from pydantic import BaseModel
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnableParallel, RunnablePassthrough, RunnableLambda

def ask(template, model=llm):              # tiny helper: one-prompt chain from a string
    return ChatPromptTemplate.from_template(template) | model | StrOutputParser()

text = "The new SmartBottle keeps drinks cold for 24h, but the lid broke after two weeks."

# 1) FAN-OUT — same input, several chains, run concurrently → dict of results
analysis = RunnableParallel(
    summary  = ask("Summarise in one sentence: {text}"),
    keywords = ask("Give 3 comma-separated keywords for: {text}", extractor),
    sentiment= ask("Answer positive, negative or mixed only: {text}", extractor),
)
print(analysis.invoke({"text": text}))

# 2) ENRICH — keep the input keys and add new ones step by step (≈ SequentialChain in 2.6)
pipeline = (
    RunnablePassthrough.assign(summary=ask("Summarise in one sentence: {text}"))
    | RunnablePassthrough.assign(reply=ask("Write a 2-sentence apology email based on: {summary}", writer))
    | RunnablePassthrough.assign(n_words=RunnableLambda(lambda d: len(d["reply"].split())))
)
out = pipeline.invoke({"text": text}); print(out.keys())   # text, summary, reply, n_words

# 3) ROUTE — classify with a fixed label set, then pick the matching chain
class Route(BaseModel):
    topic: Literal["billing", "technical", "other"]
router = ChatPromptTemplate.from_template("Classify this message: {q}") | extractor.with_structured_output(Route)
chains = {
    "billing":   ask("You are a billing expert. Answer briefly: {q}"),
    "technical": ask("You are a technical support engineer. Give numbered steps: {q}"),
    "other":     ask("Answer politely and briefly: {q}"),
}
def route(d):                               # returning a Runnable from a lambda = it gets executed
    return chains[d["route"].topic]
support = RunnablePassthrough.assign(route=router) | RunnableLambda(route)
print(support.invoke({"q": "My app shows error 503 when syncing"}))

# 4) VOTE — self-consistency (1.6): sample several reasoning paths, keep the majority answer
puzzle = "When I was 6 my sister was half my age. Now I'm 70. How old is my sister? End with 'ANSWER: <number>'."
sampler = ask("{p}", make_llm("creative"))
answers = [r.split("ANSWER:")[-1].strip(" .") for r in sampler.batch([{"p": puzzle}] * 5, config={"max_concurrency": 2})]
print(answers, "→ majority:", Counter(answers).most_common(1)[0][0])   # 67

Key takeaways

Why it matters
  • RAG = RunnableParallel(context=retriever, question=passthrough) | prompt | llm. Routing = choosing between several retrievers. Agents in LangGraph = routing in a loop.
  • Several small prompts are easier to test and debug than one long one (prompt chaining, 1.6).
Common pitfalls
  • RunnableParallel output replaces the input; use .assign when later steps still need the original keys.
  • Routing on free text ("Billing." vs "billing") breaks the dict lookup; use Literal structured output.
Remember
  • sequence | · fan-out RunnableParallel · enrich .assign · route = classifier + lookup · vote = batch + Counter.
🧠 Active recall: answer before you open
After RunnableParallel(a=..., b=...) the next step needs the original {text} and fails. Two fixes?
(1) Add a pass-through key inside the parallel: text=lambda d: d["text"]. (2) Better: use RunnablePassthrough.assign(a=..., b=...), which keeps all input keys.
Toolkit · Pattern P6

P6 · Chat memory per user session (modern replacement for ConversationBufferMemory)

⏱ ~4 min💻 1 code cell🧩 skills 5, 10📖 learn first: 2.6, 2.3
In a nutshellThe model is stateless: it only "remembers" what you resend. Memory = store the messages per session_id and inject them through a MessagesPlaceholder. RunnableWithMessageHistory does the read → call → write cycle for you; trim_messages keeps the history short.
🎯 Use it when
  • Any chatbot, tutor or assistant where follow-ups ("and the second one?") must work.
  • Several users at once (one history per session id).
💡 In plain words

A waiter with a notebook per table: before answering, they reread the last few lines for your table, then write your new order down.

# P6 · session memory
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder
from langchain_core.chat_history import InMemoryChatMessageHistory
from langchain_core.runnables.history import RunnableWithMessageHistory
from langchain_core.messages import trim_messages
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a friendly fitness coach. Keep answers under 80 words."),
    MessagesPlaceholder("history"),            # past messages are inserted here
    ("human", "{input}"),
])

# keep only the last 6 messages (token_counter=len counts messages; pass llm to count real tokens)
trimmer = trim_messages(max_tokens=6, strategy="last", token_counter=len, start_on="human")
chain = ({"input": lambda d: d["input"], "history": lambda d: trimmer.invoke(d["history"])}
         | prompt | llm | StrOutputParser())

store = {}                                     # session_id → history (use a DB/Redis in production)
def get_history(session_id: str):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

bot = RunnableWithMessageHistory(chain, get_history,
                                 input_messages_key="input", history_messages_key="history")

cfg_ana = {"configurable": {"session_id": "ana"}}
cfg_bob = {"configurable": {"session_id": "bob"}}
print(bot.invoke({"input": "Hi, I'm Ana and I want to run 5 km."}, config=cfg_ana))
print(bot.invoke({"input": "What's my name and my goal?"}, config=cfg_ana))   # remembers
print(bot.invoke({"input": "What's my name?"}, config=cfg_bob))               # separate session: doesn't know
print(len(store["ana"].messages), "messages stored for ana")

Key takeaways

Why it matters
  • Conversational RAG needs history to rewrite follow-up questions ("What about its price?") into standalone queries.
  • History is the biggest hidden token cost in a chatbot; trimming or summarising it keeps cost and latency flat.
Common pitfalls
  • Forgetting config={"configurable": {"session_id": ...}} → error or every user shares one memory.
  • Key names must match: input_messages_key ↔ {input}, history_messages_key ↔ MessagesPlaceholder("history").
  • In-memory store disappears when the Colab runtime restarts.
Remember
  • Course API ConversationBufferMemory + ConversationChain ≈ modern RunnableWithMessageHistory + MessagesPlaceholder.
Toolkit · Pattern P7

P7 · Tool calling: from the course's ReAct agent to modern bind_tools

⏱ ~7 min💻 1 code cell🧩 skills 11, 15📖 learn first: 2.7
In a nutshellThe model never runs code. It proposes a tool call (name + JSON arguments); your code runs the tool and sends the result back as a ToolMessage; repeat until the model answers. That loop is an agent. The tool's name, docstring and type hints are the prompt the model reads to decide.
🎯 Use it when
  • The answer needs live data or exact computation (prices, dates, math, database lookups).
  • The model must take actions (send email, create ticket) — with confirmation.
💡 In plain words

A manager (LLM) with assistants (tools). The manager writes a note "Calculator: 23*19"; the assistant does it and returns the note; the manager writes the final reply.

The ReAct loop of 2.7 (Thought → Action → Observation → … → Final Answer) implemented with native tool calling.
# P7 · tool calling loop (native function calling — no text parsing, no "handle_parsing_errors")
import ast, operator as op
from langchain_core.tools import tool
from langchain_core.messages import HumanMessage, SystemMessage, ToolMessage

_OPS = {ast.Add: op.add, ast.Sub: op.sub, ast.Mult: op.mul, ast.Div: op.truediv, ast.Pow: op.pow, ast.USub: op.neg}
def _safe_eval(node):                         # arithmetic only — NEVER eval() text written by a model
    if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)): return node.value
    if isinstance(node, ast.BinOp):   return _OPS[type(node.op)](_safe_eval(node.left), _safe_eval(node.right))
    if isinstance(node, ast.UnaryOp): return _OPS[type(node.op)](_safe_eval(node.operand))
    raise ValueError("only numbers and + - * / ** are allowed")

@tool
def calculator(expression: str) -> str:
    """Evaluate an arithmetic expression such as '23 * 19 + 4'. Use for ANY math."""
    try:    return str(_safe_eval(ast.parse(expression, mode="eval").body))
    except Exception as e: return f"Error: {e}"          # errors go back to the model as text

@tool
def get_order_status(order_id: str) -> str:
    """Look up the shipping status of an order by its id, e.g. 'A-991'."""
    fake_db = {"A-991": "in transit, arrives Friday", "B-123": "delivered"}
    return fake_db.get(order_id.strip().upper(), "order not found")

tools = [calculator, get_order_status]
tools_by_name = {t.name: t for t in tools}
llm_tools = llm.bind_tools(tools)            # the model now sees the tools' names, docstrings and arg types

def run_agent(question: str, max_steps: int = 5) -> str:
    messages = [SystemMessage("Use the tools when helpful. Be brief."), HumanMessage(question)]
    for step in range(max_steps):            # = AgentExecutor(max_iterations=5)
        ai = llm_tools.invoke(messages)
        messages.append(ai)
        if not ai.tool_calls:                # no more actions → final answer
            return ai.text
        for call in ai.tool_calls:           # Action → Observation
            print(f"  🔧 {call['name']}({call['args']})")
            result = tools_by_name[call["name"]].invoke(call["args"])
            messages.append(ToolMessage(content=result, tool_call_id=call["id"]))
    return "Stopped: too many steps."

print(run_agent("Where is order a-991, and what is 23*19+4?"))

P8 · Mini RAG with sources: your bridge to Course 2

⏱ ~8 min💻 1 code cell🧩 skills 6, 9📖 learn first: 2.5, 1.8
In a nutshellRAG = Retrieve the relevant chunks, Augment the prompt with them, Generate an answer grounded in them. Two phases: indexing once (load → split → embed → store) and querying per question (retrieve → prompt → LLM). Return the sources so users can check the answer.
🎯 Use it when
  • Questions about your documents (policies, manuals, papers) that the model never saw.
  • You need answers with citations and fewer hallucinations.
💡 In plain words

An open-book exam: first build the book's index (indexing); for each question, open the right pages (retrieve) and answer only from them (generate).

Everything from lesson 2.5 connected into one working pipeline.
# P8 · mini RAG with page citations
!pip install -q -U langchain-community langchain-text-splitters pypdf
from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_chroma import Chroma
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnableParallel, RunnablePassthrough

# ── Indexing (run once) ─────────────────────────────────────────────
docs = PyPDFLoader("https://arxiv.org/pdf/1706.03762").load()      # any PDF path or URL; 1 Document per page
splitter = RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=100)
chunks = splitter.split_documents(docs)                             # metadata (page, source) is kept
print(len(docs), "pages →", len(chunks), "chunks")
store = Chroma.from_documents(chunks, embeddings, collection_name="attention_paper")
retriever = store.as_retriever(search_kwargs={"k": 4})

# ── Querying ────────────────────────────────────────────────────────
def format_docs(docs):
    return "\n\n".join(f"[p.{d.metadata.get('page', 0) + 1}] {d.page_content}" for d in docs)

prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer ONLY from the context. If the answer is not there, say \"I don't know\". "
               "Cite pages like [p.3]."),
    ("human", "Context:\n{context}\n\nQuestion: {question}"),
])
answer_chain = prompt | make_llm("precise") | StrOutputParser()

rag = (RunnableParallel(docs=retriever, question=RunnablePassthrough())        # retrieve once…
       | RunnablePassthrough.assign(context=lambda d: format_docs(d["docs"]))  # …format…
       | RunnablePassthrough.assign(answer=answer_chain))                      # …answer, keep docs

out = rag.invoke("Why do the authors use multi-head attention?")
print(out["answer"])
print("Sources:", sorted({d.metadata["page"] + 1 for d in out["docs"]}))

# debugging habit: look at what was retrieved BEFORE judging the answer
for d in retriever.invoke("What optimizer was used?"):
    print(d.metadata["page"] + 1, d.page_content[:120].replace("\n", " "), "…")

Key takeaways

Why it matters
  • This is the "hello world" of Course 2. Everything after it improves one box: better splitting, hybrid search, re-ranking, query rewriting, evaluation.
  • "Answer only from context + say I don't know" is the cheapest hallucination guard.
Common pitfalls
  • Bad answer? Check retrieval first. If the right chunk isn't in the top-k, no prompt will fix it.
  • Re-running from_documents in the same collection duplicates chunks. Use a new collection_name or delete it first.
  • Chunks too small lose context; too large dilute similarity. Start 500–1000 chars, overlap 10–20%.
Remember
  • Index once: load → split → embed → store. Per query: retrieve → format → prompt → LLM → answer + sources.
🧠 Active recall: answer before you open
Your RAG bot answers confidently but wrong. What do you check first, and how?
The retrieval: call retriever.invoke(question) and read the chunks. If the right text isn't there, fix splitting / k / embeddings / query, not the prompt.
Why keep metadata when splitting?
It carries the source and page number, which you need for citations, filtering (e.g. only one document) and debugging.

# P9 · evaluation harness
import time, pandas as pd
from typing import Literal
from pydantic import BaseModel, Field
from langchain_core.prompts import ChatPromptTemplate

tests = [  # (input, expected) — grow this list every time you find a failure
    ("The package arrived crushed and late", "negative"),
    ("Works exactly as described, love it", "positive"),
    ("Good battery, but the screen scratches easily", "mixed"),
    ("Absolutely terrible customer service", "negative"),
    ("Fast delivery and great price!", "positive"),
    ("Nice design; the app keeps crashing though", "mixed"),
]
prompts = {
    "zero-shot": "Classify the sentiment as positive, negative or mixed. Reply with one word.\nReview: {x}",
    "few-shot":  "Classify the sentiment as positive, negative or mixed. Reply with one word.\n"
                 "Review: Great sound, weak bass → mixed\nReview: Broke on day one → negative\nReview: {x} →",
}
candidates = [(m, p) for m in (CONFIG["chat_model"], CONFIG["cheap_model"]) for p in prompts]

rows = []
for model_name, prompt_name in candidates:
    chain = ChatPromptTemplate.from_template(prompts[prompt_name]) | make_llm("precise", model=model_name)
    t0 = time.perf_counter()
    msgs = chain.batch([{"x": x} for x, _ in tests], config={"max_concurrency": 2})   # AIMessages (keep usage info)
    secs = time.perf_counter() - t0
    preds = [m.text.strip().lower().strip(".") for m in msgs]
    rows.append({
        "model": model_name, "prompt": prompt_name,
        "accuracy": sum(p == y for p, (_, y) in zip(preds, tests)) / len(tests),
        "sec_per_call": round(secs / len(tests), 2),
        "tokens": sum((m.usage_metadata or {}).get("total_tokens", 0) for m in msgs),
        "errors": [x for p, (x, y) in zip(preds, tests) if p != y],          # read these!
    })
pd.DataFrame(rows).sort_values(["accuracy", "sec_per_call"], ascending=[False, True])

    organization: Optional[str] = Field(None, description="نام دستگاه مناقصه‌گزار")
    tender_number: Optional[str] = Field(None, description="شماره مناقصه یا شماره فراخوان در سامانه ستاد")

    deadline_jalali: Optional[str] = Field(None, description="آخرین مهلت ارسال پیشنهاد، YYYY/MM/DD")

💻 Cell 7 · the chain (extractor.build_chain)
def build_chain(model="gemini-3.8-flash", few_shot=True, fallback="gemini-2.5-flash"):
    parser = JsonOutputParser(pydantic_object=TenderCard)
    prompt = (FEW_SHOT if few_shot else ZERO_SHOT).partial(format_instructions=parser.get_format_instructions())
    llm = get_llm(model)
    if fallback and fallback != model:
        llm = llm.with_fallbacks([get_llm(fallback)])     # Module 2: Runnable fallbacks
    return prompt | llm | parser                          # LCEL pipe

⏱ ~6 min💻 2 code cells🧠 2 recall Qs

💡 In plain words

The vector store is the warehouse (stores vectors). The retriever is the clerk who answers “give me documents for this question”. A retriever does not have to store anything; it only has to return documents.

⬅ Builds on D.0 Which retriever?
➡ Leads to D.2 Multi-query & self-query

How MMR decides (the one formula worth knowing)

MMR first fetches fetch_k candidates by similarity, then picks k of them one at a time. Each next pick maximises:

score(d) = λ · sim(question, d) − (1 − λ) · max sim(d, already picked)

  • lambda_mult = λ. 1.0 → pure relevance (same as similarity search). 0.0 → maximum diversity. 0.5 (default) is a good start.
  • The second term punishes a chunk that is similar to one you already picked, so near-duplicates are skipped.

LlamaIndex retrievers: keyword (BM25), summaries and hybrid fusion (RRF)

⏱ ~7 min💻 2 code cells🧠 3 recall Qs
In a nutshellVector search finds meaning but can miss exact words (product codes, names, error IDs). BM25 finds exact words but misses synonyms. Hybrid search runs both and merges the two ranked lists with Reciprocal Rank Fusion (RRF): score = Σ 1/(rank + 60). In LlamaIndex this is one QueryFusionRetriever.

💡 In plain words

Two judges rank the same documents: one judges by meaning, one by exact words. RRF rewards documents that both judges place near the top, without needing their scores to be on the same scale.

2 · BM25 in two sentences

BM25 scores a chunk higher when it contains the query words often (with diminishing returns, k1≈1.2), when those words are rare in the whole collection (IDF — "the" counts for nothing), and it slightly penalises long chunks (b≈0.75). No embeddings, no API calls — it is fast and free.

3 · RRF worked example (k = 60)

ChunkVector rankBM25 rankRRF score
A131/61 + 1/63 = 0.0323
B2—1/62 = 0.0161
C—11/61 = 0.0164
D321/63 + 1/62 = 0.0320

Final order: A, D, C, B — chunks found by both methods win. Only ranks are used, so a cosine score (0–1) and a BM25 score (0–20+) never need to be compared. Other mode options: relative_score (min-max normalise scores, then add) and dist_based_score (normalise using mean ± 3 std).

# ── D.4a · RRF in 6 lines (no libraries) — check the table above ──
def rrf(rank_lists, k=60):
    scores = {}
    for ranks in rank_lists:
        for r, doc in enumerate(ranks, start=1):
            scores[doc] = scores.get(doc, 0) + 1 / (r + k)
    return sorted(scores, key=scores.get, reverse=True)

print(rrf([["A", "B", "D"], ["C", "D", "A"]]))   # ['A', 'D', 'C', 'B']

Why does RRF use ranks instead of scores?
Vector and BM25 scores are on different scales; ranks are comparable across any retriever, so no normalisation is needed.

Rank 2 in both: 2/62 ≈ 0.0323 > 1/61 ≈ 0.0164. Agreement beats a single top spot.

It searches LLM-written summaries of each document, then returns that document's original chunks.

Vector databases: FAISS vs Chroma, index types and HNSW knobs

⏱ ~7 min💻 2 code cells🧠 3 recall Qs
In a nutshellFAISS is a fast similarity-search library (vectors only, you manage files and metadata). Chroma is a small vector database (vectors + metadata + filters + persistence). Both answer "which stored vectors are closest to this one?" Exact search (Flat) compares with everything; approximate indexes (IVF, LSH, HNSW) skip most vectors to be fast. HNSW is the usual choice; tune it with M, efConstruction, efSearch.

# !pip install -q faiss-cpu
import faiss, numpy as np, time
d, n = 128, 50_000
X = np.random.rand(n, d).astype("float32"); q = np.random.rand(5, d).astype("float32")

flat = faiss.IndexFlatL2(d); flat.add(X)                 # exact, brute force
hnsw = faiss.IndexHNSWFlat(d, 32)                         # M = 32
hnsw.hnsw.efConstruction = 200; hnsw.add(X)

t = time.time(); D_ex, I_ex = flat.search(q, 10); print("flat  ms:", round((time.time()-t)*1000, 1))
for ef in [16, 64, 256]:
    hnsw.hnsw.efSearch = ef
    t = time.time(); D, I = hnsw.search(q, 10)
    recall = np.mean([len(set(I[i]) & set(I_ex[i])) / 10 for i in range(len(q))])
    print(f"hnsw ef={ef:3d}  ms={(time.time()-t)*1000:5.1f}  recall@10={recall:.2f}")   # ef↑ → recall↑

🧠 Active recall: answer before you open
What is the main practical difference between FAISS and Chroma?
FAISS is a library that stores and searches vectors only (no native metadata filtering, you save files yourself); Chroma is a database that also stores metadata, filters on it, and persists data.
Which HNSW parameter do you change at query time to trade speed for recall?
efSearch — higher means more candidates checked, higher recall, slower queries.
Why can IVF miss the true nearest neighbour?
It searches only the few cells closest to the query; a true neighbour sitting in an unsearched cell is skipped (raise nprobe to reduce this).

Common failures & fixes
  • NoTranscriptFound / TranscriptsDisabled: the video has no English captions — try another video or languages=["en", "de", …].

One-page cheat sheet

GenAI basics

Discriminative = boundaries P(y|x) · Generative = distribution, new content · Foundation model = pre-trained, adapt with little data · NLU text→structure · NLG structure→text · Predict behaviour = ML.

Prompt = 4 elements

Instructions · Context · Input data · Output indicator. Benefits: accuracy, relevance, meets expectations, no continual fine-tuning.

Techniques

Zero-shot (0 ex) · One-shot (1) · Few-shot (2–5) · CoT “step by step” · Self-consistency (many paths, vote) · Prompt chaining. In-context learning = examples at inference, no weight change.

Generation params

max_new_tokens→max_output_tokens · temperature 0.1 classify / 0.7 creative · top_p · top_k · min_new_tokens (watsonx only) · stop.

LCEL

Template {vars} → PromptTemplate → prompt | llm | StrOutputParser() → .invoke({…}). RunnableSequence = pipe; RunnableParallel = same input, concurrent; RunnableLambda wraps fn; dict/fn auto-coerced; RunnablePassthrough.assign adds keys.

LangChain components

LLM · Chat model · Messages (Human/AI/System/Function/Tool) · Prompt templates · Example selectors · Output parsers · Documents · Splitters · Embeddings · Vector stores · Retrievers · Memory · Chains · Agents/Tools.

Parsers

JSON → JsonOutputParser(pydantic_object=…) + get_format_instructions() · CSV list → CommaSeparatedListOutputParser · string → StrOutputParser.

Retrieval stack

PyPDFLoader/WebBaseLoader → RecursiveCharacterTextSplitter(chunk_size, chunk_overlap) → embeddings → Chroma.from_documents → similarity_search / as_retriever() · ParentDocumentRetriever (child search, parent return, InMemoryStore).

Memory & chains

Memory reads/writes history → continuity. ChatMessageHistory, ConversationBufferMemory + ConversationChain. LLMChain(output_key) → SequentialChain(input_variables, output_variables) ≡ LCEL .assign().

Agents

LLM chooses actions. Tool(name, func, description) / @tool · create_react_agent(llm, tools, prompt) · AgentExecutor(handle_parsing_errors, max_iterations) · ReAct: Thought→Action→Observation→Final Answer.

Tokenize (BPE) → Embed → Attention (multi-head) → Layers (+residual) → Next-token → Inference token-by-token; temperature/sampling.
