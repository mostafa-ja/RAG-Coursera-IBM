Different models produce vectors of different sizes and different “meaning spaces”; distances between them are meaningless. One index = one embedding model.

Retrievers & the vector-store retriever: similarity, MMR, threshold

⏱ ~12 min🧭 2 diagrams💻 3 code cells🧠 3 recall Qs
In a nutshellA retriever is an interface: string query in → list of Documents out. The simplest one wraps a vector store: vectordb.as_retriever(). Choose its search_type: similarity (top-k closest, default k = 4), mmr (relevant and different from each other) or similarity_score_threshold (only results above a score).
🎯 After this lesson you can
  • Explain retriever vs vector store in one sentence each.
  • Create a vector-store retriever and set k, search_type and search_kwargs.
  • Pick similarity, MMR or threshold for a given problem (lab Exercise 1).
💡 In plain words

The vector store is the bookshelf; the retriever is the person you ask. “Similarity” brings the 4 closest books. “MMR” brings 4 close books but no two copies of the same one. “Threshold” brings only books that really match — maybe 1, maybe none.

⬅ Builds on 0.2 Colab setup and Course 3 (Chroma, similarity search)
➡ Leads to 1.2 Multi-Query

Every retriever in this course — LangChain or LlamaIndex — has this shape. That is why you can swap one for another, or fuse several (1.8).

Retriever vs vector store

A vector store (Chroma, FAISS, Milvus…) stores embeddings plus text and metadata and can search them. A retriever only has to return relevant documents for a query; it may use a vector store, a keyword index (BM25), an LLM, a web API or several of these. In LangChain every retriever is a Runnable, so you call it with .invoke(query) and can put it inside an LCEL chain.

How MMR chooses

MMR (Maximal Marginal Relevance) first fetches fetch_k = 20 candidates, then picks k = 4 one by one. Each step takes the candidate with the best λ · similarity(query) − (1 − λ) · max similarity(already picked). lambda_mult = 1 → pure similarity; 0 → pure diversity; the default 0.5 balances both. Use it when your top-k is full of near-duplicate chunks (overlapping splits, repeated boilerplate).

Key takeaways

Why it matters
  • Every later retriever (multi-query, self-query, parent document, ensembles) is built on top of this one; its k and search type still matter there.
  • The retriever interface makes RAG code provider-independent: swap Chroma for FAISS (2.5) and the chain does not change.
Common pitfalls
  • Passing k directly (as_retriever(k=2)) — it belongs in search_kwargs={"k": 2}.
  • Copying a threshold (0.4) from a tutorial: scores depend on model + metric; print them first.
  • Re-running Chroma.from_documents in the same session adds the chunks again → duplicates in results. Delete the old ids or use a fresh collection_name.
Remember
  • Query string in, list[Document] out, via .invoke().
  • Defaults: k = 4; MMR fetch_k = 20, lambda_mult = 0.5.
🧠 Active recall: answer before you open
What is the difference between a retriever and a vector store?
A vector store stores embeddings (with text and metadata) and can search them. A retriever is an interface that returns relevant documents for an unstructured query; it can be backed by a vector store or by anything else (keywords, LLM, API).
Your top 4 results are four overlapping copies of the same paragraph. Which search type helps, and why?
search_type="mmr": it penalises candidates that are similar to chunks already picked, so the 4 results cover different content.
Why can a similarity_score_threshold retriever return an empty list?
It only returns chunks whose relevance score is above the threshold; if no chunk is close enough (or the threshold is too high for this embedding model), nothing passes.

Multi-Query retriever: let the LLM ask the question three ways

⏱ ~10 min🧭 1 diagram💻 2 code cells🧠 3 recall Qs
In a nutshellDistance-based search is sensitive to wording. MultiQueryRetriever asks an LLM to rewrite the question into 3 variants, runs the base retriever once per variant and returns the unique union of all hits. More recall and variety, at the price of one LLM call and N searches.
🎯 After this lesson you can
  • Explain which weakness of vector search Multi-Query fixes.
  • Wrap any retriever with MultiQueryRetriever.from_llm() and see the generated queries in the log.
  • Predict how many documents come back (≤ variants × k, minus duplicates).
💡 In plain words

You ask a librarian “laptop for personal stuff?” and get odd answers. A smart friend first rephrases it: “personal use of company computers”, “private use of company devices”, “internet and email at work for personal reasons”. The librarian searches for each one and you get all the books in one pile, without copies.

⬅ Builds on 1.1 Vector-store retriever
➡ Leads to 1.3 Self-Query · fusion with ranks in 1.8

Why one query is not enough

An embedding puts the query at one point in vector space. If the user’s words differ from the document’s words (“laptop” vs “company-provided devices”), the closest chunks may be off-topic, and a small change of wording can change the whole top-k. Multi-Query attacks this by searching from several points at once.

Real counts from the offline run below (122 policy chunks, k = 4). The duplicate was the “Acceptable Use: Company-provided internet and email…” chunk, found by both q2 and q3. The original question itself is not searched unless you pass include_original=True.

The default prompt (and how to change it)

LangChain’s built-in prompt says: “generate 3 different versions of the given user question to retrieve relevant documents from a vector database … Provide these alternative questions separated by newlines.” Each output line becomes one query. Pass your own PromptTemplate with prompt= to ask for 5 variants, another language, or domain synonyms; include_original=True also searches the user’s own wording.

Key takeaways

Why it matters
  • Users rarely use the document’s words; rewrites close the vocabulary gap.
  • It wraps any retriever, so it combines with MMR, filters or BM25.
Common pitfalls
  • Expecting a ranking: the result is a union, not a re-ranked list, and can contain noise from a bad rewrite.
  • Extra cost and latency: 1 LLM call + 3 searches per question.
  • No log output after switching to langchain_classic: set the level on langchain_classic.retrievers.multi_query.
Remember
  • LLM → 3 variants (default) → retrieve each → unique union.
  • Max docs = variants × k; duplicates removed.

Parent Document retriever: search small, return big

⏱ ~10 min🧭 2 diagrams💻 4 code cells🧠 3 recall Qs
In a nutshellSmall chunks give sharp embeddings; big chunks give the LLM enough context. ParentDocumentRetriever keeps both: a child splitter makes small chunks that go into the vector store, a parent splitter makes large chunks that go into a separate docstore. A query is matched against the children, and the retriever returns their parents.

💡 In plain words

A book index lists single lines (“smoking, p. 42”). The index line helps you find the place, but you then read the whole page. Children are the index lines, parents are the pages, and the retriever turns to the page for you.

⬅ Builds on 1.1 Vector-store retriever (same txt_data, embeddings)
➡ Leads to 1.5 LlamaIndex · the same idea with merging in 1.7 Auto-merging

Two wishes that fight each other

The lab names the problem: (1) you want small documents so that one embedding reflects one meaning — a long chunk mixes topics and its vector becomes an average of them; (2) you want long documents so the context of each chunk is kept — a 200-character chunk such as "5.\tSmoking Policy" matches the query well but tells the LLM nothing. One chunk size cannot satisfy both, so the retriever uses two sizes for two jobs: children for matching, parents for answering.

Real counts from the offline run of the lab code below (companypolicies.txt, lab splitter settings). Parents are 337–989 chars (avg 823), children 17–694 chars.

2 · BM25 Retriever: exact words, better than TF-IDF

TF-IDF scores a word high when it is frequent in this document (TF) and rare in the collection (IDF). It has two problems: the score grows linearly with repetitions (100 mentions = 10 × the score of 10), and long documents win because they contain more words. BM25, the default ranking in Elasticsearch and Lucene, fixes both:

BM25 in one line

score(q, d) = Σterm t in q IDF(t) · tf·(k1 + 1) / (tf + k1·(1 − b + b·|d| / avgdl))

  • k1 (lab ≈ 1.2; bm25s default 1.5) = saturation: more repetitions help less and less. Offline: a node with “neural” 1× scores 0.060, 2× 0.073, 5× 0.084, 20× only 0.091.
  • b (0.75) = length normalisation: 0 = none, 1 = full; long documents are scored relative to the average length avgdl.
  • IDF: a word in every document (“learning” here) adds little; a rare one (“neural”) adds a lot.

# Cell 18 · lab Exercise 1 — vector 0.7 + BM25 0.3 on max-normalised scores
vector_r = lab.vector_index.as_retriever(similarity_top_k=10)
bm25_r = BM25Retriever.from_defaults(nodes=lab.nodes, similarity_top_k=10)

def hybrid_retrieve(query, top_k=5, w_vec=0.7, w_bm25=0.3):
    v, b = vector_r.retrieve(query), bm25_r.retrieve(query)
    mv = max([r.score for r in v]) if v else 1          # divide by the best score → top hit = 1.0
    mb = max([r.score for r in b]) if b else 1
    vs = {r.text.strip(): r.score / mv for r in v}      # key = text: node ids differ between the two indexes
    bs = {r.text.strip(): r.score / mb for r in b}
    rows = [(w_vec * vs.get(t, 0) + w_bm25 * bs.get(t, 0), vs.get(t, 0), bs.get(t, 0), t)
            for t in set(vs) | set(bs)]
    return sorted(rows, reverse=True)[:top_k]

🧠 Active recall: answer before you open
Name the two TF-IDF problems BM25 fixes and the parameter for each.
Linear term-frequency growth → saturation controlled by k1 (≈ 1.2–1.5): extra repetitions add less and less. Long-document bias → length normalisation controlled by b (0.75; 0 = none, 1 = full), relative to the average document length.
LLM vs embedding Document Summary retriever: what differs, and what do both return?
The LLM version sends the summaries (in batches, default 10) with the question to the LLM and asks for document numbers with relevance scores: smarter but slower and paid per call (choice_top_k). The embedding version compares the query embedding with summary embeddings: fast, no LLM call (similarity_top_k). Both return the original nodes of the chosen documents, not the summaries.
In the Exercise 1 hybrid, why is the top hit always 1.000, and why is that a problem?
Each list is divided by its own best score, so the best vector hit and the best BM25 hit both become 1.0, and 0.7 + 0.3 = 1.0. That happens for every query, even a nonsense one, so the hybrid score cannot tell “good match” from “best of a bad set” and cannot be used with a threshold.

Auto-merging & Recursive retrievers: bigger context only when it is earned

⏱ ~12 min🧭 3 diagrams💻 4 code cells🧠 3 recall Qs
In a nutshellBoth retrievers search small pieces and return bigger ones, like the Parent Document Retriever of 1.4, but with a rule. The Auto-merging retriever splits text into a tree (for example 2048 → 512 → 128 tokens), searches only the leaves, and swaps a group of leaves for their parent when more than half of that parent’s children were retrieved. The Recursive retriever follows references: a hit that is an IndexNode points to another node or retriever, and the retriever “enters” it. Without references it is just a vector retriever, and that is exactly what the lab cell shows.

💡 In plain words

A student marks sentences in a book. If they mark three sentences on one page, it is easier to photocopy the whole page. If they mark only one sentence, they copy just that sentence. Auto-merging is that rule. Recursive retrieval is a footnote: the marked sentence says “see page 12”, and you go to page 12.

From 1.4 to 1.7: the same wish, a smarter rule

In 1.4 the Parent Document Retriever always returned the parent of every child hit. That gives context, but also long, partly unrelated text when only one small child matched. The Auto-merging retriever decides per query: a parent replaces its children only when enough of them were found. Many hits in one region mean “this whole region is relevant”; one hit means “keep it small”.

Recursive retriever: follow references

The Recursive retriever does not merge by counting. It follows links. Any retrieved node that is an IndexNode carries an index_id; the retriever looks that id up in node_dict (return that node) or retriever_dict / query_engine_dict (run that retriever or query engine with the same question). Two reference types are common:

  • Chunk references: small chunks point to their big parent chunk (search small, return big, like 1.4).
  • Metadata references: a summary or a few generated questions point to the chunk they describe; for papers, a citation points to the cited paper’s retriever.

The ten doc_i retrievers are never called: the hits are plain TextNodes, and a list of ids in metadata is not a reference the retriever understands. 🧠 Active recall: answer before you open
What goes into the vector index and what into the docstore for auto-merging, and why?
Only the leaf nodes are embedded in the vector index, so search works on small, precise chunks. The docstore holds all levels (leaves, middles, roots), so the retriever can fetch a parent by id when it decides to merge.
A parent has 4 children. The retriever found 2 of them. Does it merge with the default setting? What about 3?
2 / 4 = 0.5 is not greater than simple_ratio_thresh=0.5, so no merge; the 2 leaves are returned. 3 / 4 = 0.75 > 0.5, so the 3 leaves are replaced by the parent, with the average of their scores.
Why does the lab’s recursive retriever return the same nodes as its base retriever?
Its hits are plain TextNodes. Only an IndexNode with an index_id that matches a key in node_dict / retriever_dict makes the retriever follow a link. A references list in metadata is just text (and is even embedded).

Query fusion: many queries, many retrievers, one ranked list

⏱ ~14 min🧭 2 diagrams💻 4 code cells🧠 3 recall Qs
In a nutshellQueryFusionRetriever does two jobs. (1) More queries: the LLM rewrites your question (num_queries counts the original, so 3 = original + 2 rewrites, in one LLM call). (2) More retrievers: every query goes to every retriever (for example vector + BM25). Then it fuses all result lists into one: RRF adds 1/(60 + rank) and ignores scores; relative score min-max scales each list to 0–1 and adds; distribution-based scales with mean ± 3σ. With num_queries=1 there is no LLM call at all: it is a plain hybrid retriever, the pattern TenderYar uses.

💡 In plain words

You ask three friends for the best restaurant. One gives marks out of 10, one out of 100, one just a ranking. You cannot add their marks. RRF says: “1st place is worth a bit more than 2nd, whatever the marks.” Relative score says: “turn each friend’s marks into 0–1 first, then add.”

From 1.2 and 1.6 to 1.8: one class for both ideas

In 1.2 the Multi-Query retriever asked the LLM for variants and took the union. In 1.6 (Exercise 1) you fused vector and BM25 scores by hand. QueryFusionRetriever does both in one object and adds a real ranking of the union, so the document that many queries and retrievers agree on comes first.

RRF needs only the rank of a document in each list: score(d) = Σ 1 / (60 + rank), and LlamaIndex counts rank from 0, so 1st place adds 1/60 = 0.0167. Cell 24 records the three lists and recomputes the scores:

# Cell 24 · look inside: record the lists RRF fused, then recompute the scores by hand
from llama_index.core.retrievers import BaseRetriever

class Spy(BaseRetriever):                      # wraps a retriever, keeps (query, [(text, raw score)])
    def __init__(self, inner):
        super().__init__(); self.inner, self.log = inner, []
    def _retrieve(self, query_bundle):
        res = self.inner.retrieve(query_bundle)
        self.log.append((query_bundle.query_str, [(n.text, n.score) for n in res]))   # copy NOW:
        return res                             # fusion later overwrites n.score in place

spy = Spy(base_retriever)
fused = QueryFusionRetriever([spy], similarity_top_k=3, num_queries=3,
                             mode="reciprocal_rerank", use_async=False).retrieve(query)
for q, res in spy.log:
    print(repr(q[:40]), [t.split()[0] for t, s in res])

def manual_rrf(lists, k=60):                   # LlamaIndex counts rank from 0 → best = 1/60
    score = {}
    for lst in lists:
        for rank, (text, s) in enumerate(sorted(lst, key=lambda x: x[1], reverse=True)):
            score[text] = score.get(text, 0) + 1 / (rank + k)
    return sorted(score.items(), key=lambda x: -x[1])

for (t, s), n in zip(manual_rrf([res for _, res in spy.log]), fused):
    print(f"manual {s:.4f} | library {n.score:.4f}  {t[:40]}")

Silent traps (all tested offline)
  • num_queries counts the original: 3 → 2 LLM variants. 1 → no LLM call.
  • Numbered variants are searched with the number (“1. machine …”).
  • RRF ignores retriever_weights: no error, no warning, same scores.
  • Relative score is min-max, not /max: the last hit of every list gets 0, so a document that is last everywhere scores 0.
  • No absolute threshold: the top of a relative list is always ≈ 1, and RRF scores have no 0–1 meaning. “Score > 0.8” filters nothing useful.
  • Scores are overwritten in place: copy raw scores before fusing.
  • Defaults: simple mode, 4 queries, top 2.

Key takeaways

Why it matters
  • Fusion lets keyword search and meaning search vote; documents both agree on rise to the top.
  • RRF works without knowing anything about score scales, so it is the safe choice for vector + BM25.
Common pitfalls
  • Using simple (the default) to mix cosine and BM25 scores.
  • Setting weights with RRF and believing they work.
  • Paying for LLM variants when a second retriever would help more.
