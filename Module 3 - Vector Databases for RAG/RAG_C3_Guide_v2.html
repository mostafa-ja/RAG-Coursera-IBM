An embedding function is the object Chroma calls to turn documents (and queries) into vectors. When you pass it in configuration={"embedding_function": ef}, Chroma embeds automatically on add and query. The notebooks write this class to a file so the lab scripts (run with !python …) can import it.

# Chroma embedding function backed by Gemini (replaces SentenceTransformerEmbeddingFunction("all-MiniLM-L6-v2"))
import os
os.environ.setdefault("ANONYMIZED_TELEMETRY", "False")
from chromadb import Documents, EmbeddingFunction, Embeddings
from langchain_google_genai import GoogleGenerativeAIEmbeddings

class GeminiEmbeddingFunction(EmbeddingFunction):
    def __init__(self, model: str = "models/gemini-embedding-2"):
        self.model = model
        self._emb = GoogleGenerativeAIEmbeddings(model=model)   # key read from GOOGLE_API_KEY

    def __call__(self, input: Documents) -> Embeddings:
        texts = list(input)
        out = []
        for i in range(0, len(texts), 100):              # free tier: <= 100 texts per call
            out += self._emb.embed_documents(texts[i:i + 100])
        return out

    @staticmethod
    def name() -> str:
        return "gemini"

    def get_config(self):
        return {"model": self.model}

    @staticmethod
    def build_from_config(config):
        return GeminiEmbeddingFunction(config.get("model", "models/gemini-embedding-2"))

Core idea 1 of 7

Embeddings: meaning turned into coordinates

⏱ ~4 min💻 1 code cell🧠 2 recall Qs
In a nutshellAn embedding model turns a piece of text into a fixed-length list of numbers, a vector (for example 768 or 3072 numbers). Texts with similar meaning get vectors that point in similar directions. A vector database stores these vectors and finds the ones closest to the vector of your question. That is all “semantic search” means.
🛠 You use this when
  • you search by meaning, not by exact words (“low-cost airline tickets” should find “cheap flights”);
  • you choose what text to embed for each record in a project.
💡 In plain words

Think of a huge map where every sentence gets a position. Sentences about the same thing land close together, even if they share no words. A query is just one more point on the map; search means “show me the nearest points”.

TextToy 2-D vectorClose to the query “low-cost airline tickets” [0.86, 0.14]?
cheap flights to Rome[0.90, 0.10]✅ Yes. Same direction, no shared words.
budget travel tips[0.70, 0.30]🟡 Somewhat.
chocolate cake recipe[0.10, 0.95]❌ No. Points another way.

Real models use hundreds or thousands of dimensions instead of two, but the idea is the same. You never read these numbers yourself; you only compare them.

Two rules that matter in every project

  1. One model per collection. Documents and queries must be embedded by the same model. Vectors from two different models live on two different maps, so comparing them is meaningless. If the dimensions differ, Chroma raises an error; if they match, you silently get bad results.
  2. What you embed is what you can find. The model only sees the text you pass in. For a food record, embed “name + description + cuisine + ingredients”, not just the name. Keep fields you want to filter on (price, calories, city) as metadata (idea 3).

In code (Chroma does the embedding for you)

ef = GeminiEmbeddingFunction()          # from gemini_ef.py (see Start here · 0.2)
col = client.get_or_create_collection("notes",
        configuration={"hnsw": {"space": "cosine"}, "embedding_function": ef})

col.add(ids=["n1", "n2"],
        documents=["cheap flights to Rome", "chocolate cake recipe"])   # ef embeds the documents

col.query(query_texts=["low-cost airline tickets"], n_results=1)       # ef embeds the query → returns n1

Because the embedding function is attached to the collection, the same model is used for add and query automatically. This is the easiest way to obey rule 1.

Key takeaways

Why it matters
  • Search quality starts here. A good model with well-chosen embedding text beats any index tuning you do later.
Mistake to avoid
  • Switching the embedding model on an existing collection. Instead, create a new collection and re-embed everything (P3 · clone to change model).
Remember
  • Similar meaning → nearby vectors. Same model for add and query. Embed the descriptive text; store filterable fields as metadata.

Why can “low-cost airline tickets” find “cheap flights to Rome” although they share no words?
Both texts are embedded into vectors that point in almost the same direction, because they mean the same thing. Search compares vectors, not words.
You switch to a new embedding model but keep the old collection. What goes wrong, and what is the fix?
The stored vectors came from the old model, so queries embedded with the new model are compared on a different “map”. You get an error (different dimensions) or silently bad results. Fix: create a new collection and re-embed all documents with the new model.
Core idea 2 of 7

Distance vs similarity: reading the numbers Chroma returns

⏱ ~5 min💻 1 code cell🧠 2 recall Qs
In a nutshellChroma always returns a distance: smaller = closer. Which distance you get depends on the space you chose when you created the collection: "l2" (the default) = squared Euclidean distance, "cosine" = 1 − cosine similarity, "ip" = 1 − dot product. For text, use "cosine".
🛠 You use this when
  • you print results and want to know if a hit is “good”;
  • you show a score to users or drop weak results before they reach the LLM.
💡 In plain words

Similarity = “how alike” (bigger is better). Distance = “how far apart” (smaller is better). They are two sides of one coin: distance = 1 − similarity for cosine.

spaceWhat Chroma returnsRangeTurn it into a similarity
"cosine" ✅ text1 − cos(a, b)0 (same direction) … 1 (unrelated) … 2 (opposite)similarity = 1 − d
"l2" (default)Σ(aᵢ − bᵢ)², no square root0 … ∞for unit vectors: cos = 1 − d / 2
"ip"1 − a·bcan be negative for long vectorsdot = 1 − d (= cosine if vectors are unit length)

Worked example: same pair, three numbers

Take two unit-length vectors whose cosine similarity is 0.80. Chroma reports: cosine → 1 − 0.80 = 0.20; ip → 1 − 0.80 = 0.20; l2 → 2 − 2 × 0.80 = 0.40. The ranking of results is the same in all three spaces (the vectors are normalized), only the numbers differ. That is why a value like “0.40” means nothing until you know the space.

In code: read results the right way

res = col.query(query_texts=["vegan pasta"], n_results=3)   # returns documents, metadatas, distances by default

# Results are lists of lists: one inner list per query text, so take [0] for the first query
for doc_id, doc, d in zip(res["ids"][0], res["documents"][0], res["distances"][0]):
    print(f"{doc_id}  distance={d:.3f}  similarity={1 - d:.3f}  {doc[:60]}")   # cosine space

Is 0.35 a good distance? Calibrate a threshold

There is no universal cut-off; it depends on the embedding model and the space. Run 5–10 queries where you already know the right answer, write down the distances of correct and wrong hits, and choose a value between them (for example “keep only d < 0.45”). In RAG, if nothing passes the threshold, let the app answer “I couldn't find this in the documents” instead of passing weak context to the LLM.

Key takeaways

Why it matters
  • Thresholds, scores shown to users and “no answer” logic all depend on reading the distance correctly.
Mistake to avoid
  • Sorting distances from high to low as if they were similarities.
  • Forgetting the default space is l2: always set {"hnsw": {"space": "cosine"}} for text. The space is fixed at creation; to change it, build a new collection.
Remember
  • Distance: lower = closer. Cosine distance = 1 − similarity. Chroma's l2 is squared. Take [0] for the first query.

Core idea 3 of 7

A collection = id + document + embedding + metadata

⏱ ~5 min💻 1 code cell🧠 2 recall Qs
In a nutshellA Chroma collection is like a table where every row (record) has four parts: a unique id, the document text, its embedding (made for you by the embedding function), and metadata (a small dictionary of facts such as price or city). You manage rows with add / upsert / update / delete, read them by id with get, and search them by meaning with query.
🛠 You use this when
  • you load a dataset (foods, employees, tenders, PDF chunks) into Chroma;
  • you keep it up to date or reopen it after Colab restarts.
💡 In plain words

One record = one card on a library shelf: a shelf number (id), the text on the card (document), its position on the meaning map (embedding), and labels on the cover (metadata) you can sort and filter by.

Key takeaways

Why it matters
  • Good ids and metadata make every later step easy: updates, filters, citations (“source: food_017”) and evaluation.
Mistake to avoid
  • Using chromadb.Client() (in memory) for project data: it is gone when the runtime restarts.
  • Random ids (uuid) + add in a cell you run twice: you get duplicates. Use real ids + upsert.
  • Putting None or nested dicts in metadata: turn lists into a string such as "rice, peanuts".
Remember
  • Record = id + document + embedding + metadata. get = exact, query = ranked. Persist on Drive, use upsert.

🧠 Active recall: answer before you open
What is the difference between get and query?
get fetches records exactly by id or metadata filter, with no ranking and no embedding of a query. query embeds the query text and returns the nearest records, ranked by distance.
Your loading cell uses add with uuid ids. You run it three times. What happens, and how do you fix it?
Each run inserts the same documents with new ids, so every record exists three times and searches return duplicates. Use stable ids from the data (e.g. food_017) and upsert.
Core idea 4 of 7

Filters narrow, similarity ranks

⏱ ~4 min💻 1 code cell🧠 2 recall Qs
In a nutshellA query can carry two kinds of filters. where checks metadata (“cuisine is Thai and calories ≤ 650”). where_document checks the document text (“contains ‘peanut’”). Chroma keeps only the records that pass the filters, then ranks those by distance and returns the top n_results.
🛠 You use this when
  • a user has hard rules: budget, city, department, “vegan only”, “still open”;
  • you want only records from one source, date or category in RAG.
💡 In plain words

Filters are the must rules (yes/no). Similarity is the should part (best match first). Put hard rules in where, put the fuzzy wish (“something spicy and comforting”) in the query text.

StepRecords leftWhat happened

where: Thai or Vietnamese, calories ≤ 65038Metadata rules applied

In code

res = col.query(
    query_texts=["spicy noodle dish"], n_results=5,
    where={"$and": [                                    # several conditions → wrap them in $and
        {"cuisine": {"$in": ["Thai", "Vietnamese"]}},
        {"calories": {"$lte": 650}}]},
    where_document={"$contains": "peanut"})             # case-sensitive text match

col.get(where={"cuisine": "Thai"})                       # filter without similarity: list all Thai foods

Key takeaways

Why it matters
  • Similarity alone can return a perfect match that breaks a hard rule (too expensive, wrong city). Filters guarantee the rules.
Mistake to avoid
  • Writing two keys in one dict, {"cuisine": "Thai", "calories": 500}: use $and.
  • Filters that are too strict: you get fewer than n_results, or nothing. Print col.get(where=...) to check.
  • Comparing numbers stored as strings ("650"): store numbers as int/float.
Remember
  • where → metadata. where_document → text. Filter first, then rank by similarity.

“Find Italian dishes under 700 calories that feel light and fresh.” What goes in where, and what goes in the query text?
where={"$and": [{"cuisine": "Italian"}, {"calories": {"$lt": 700}}]}. The query text is “light and fresh dish”, because that is a fuzzy wish, not a yes/no rule.

Like driving to an address: take the motorway (top layer, few long jumps), exit onto main roads (middle layers), then walk the local streets (bottom layer) to the nearest door. You don't visit every house in the country.

The vector database as the RAG retriever

⏱ ~5 min💻 1 code cell🧠 2 recall Qs
In a nutshellIn RAG (Retrieval-Augmented Generation) the vector database is the retriever: it finds the few chunks of your documents that best match the question. Your code pastes those chunks, with their ids, into the prompt, and the LLM answers from that context and cites it. The LLM brings the language skills; the database brings the facts.
🛠 You use this when
  • an LLM must answer from your own data (PDFs, policies, product lists) that it never saw in training;
  • you need answers with sources and fewer made-up facts.
💡 In plain words

An open-book exam. The database is the student's quick index to the right pages; the LLM reads only those pages and writes the answer, pointing to the page numbers.

StepWho does it

In code: a minimal, honest RAG function

def answer(question, k=4, max_dist=0.5):           # max_dist: calibrate it for your data (idea 2)
    res = col.query(query_texts=[question], n_results=k)
    hits = [(i, doc) for i, doc, d in zip(res["ids"][0], res["documents"][0], res["distances"][0])
            if d < max_dist]
    if not hits:
        return "I couldn't find this in the documents."
    context = "\n\n".join(f"[{i}] {doc}" for i, doc in hits)
    prompt = (
        "Answer the question using ONLY the context below. "
        "Cite the ids you used, like [food_017]. If the context is not enough, say so.\n\n"
        f"Context:\n{context}\n\nQuestion: {question}")
    return llm.invoke(prompt).content                # llm = ChatGoogleGenerativeAI(...) from Start here · 0.2

print(answer("Which Thai dishes contain peanuts?"))

Choosing k

Start with k = 3–5. Too few chunks and the answer misses facts; too many and the prompt fills with noise, costs more tokens and the LLM may get distracted. If answers are wrong, first print the retrieved chunks: when the right chunk is not there, fix retrieval (embedding text, chunk size, filters); when it is there, fix the prompt.

Key takeaways

Why it matters
  • This is the core pattern of the whole certificate. Every later RAG and agent project reuses this retriever.
Mistake to avoid
  • Expecting the vector DB to chunk documents, write the prompt or check the answer. It only embeds, stores and retrieves.
  • Sending context without ids: the LLM then cannot cite sources and you cannot verify the answer.
Remember
  • Retrieve top-k → filter weak hits → context with ids → “answer only from context, cite ids” → LLM.

Recommenders, and how to check that retrieval works

⏱ ~5 min💻 1 code cell🧠 2 recall Qs
In a nutshellA “more like this” recommender is a similarity search where the query is an item instead of a question: filter by the user's rules, rank by similarity, remove the item itself, and explain why each result was picked. To know whether search or recommendations are good, don't guess: measure recall@k on a small test set.
🛠 You use this when
  • you build “similar foods / books / employees / tenders” features;
  • you change the model, the embedding text or the chunking and want to know if it got better.
💡 In plain words

Recommender: “people who liked this dish may like these, within your calorie limit.” Recall@k: “for my 20 test questions, how often is the right answer somewhere in the top k results?”

Recommender recipe

  1. Rule filter with where (budget, diet, availability).
  2. Rank by similarity to the item's embedding (reuse it, no need to embed again).
  3. Drop the item itself: it is always its own best match. Ask for n + 1 results and remove it.
  4. Explain: show the similarity and the shared metadata (“also Thai · 92% similar”).

Recall@k in one sentence

Write 10–20 queries for which you know the correct id. recall@k = share of queries whose correct id appears in the top k. Example: the right food is in the top 5 for 17 of 20 queries → recall@5 = 0.85. Run it before and after every change and keep the better version.

In code

def more_like(item_id, n=3, where=None):
    item = col.get(ids=[item_id], include=["embeddings", "metadatas"])
    res = col.query(query_embeddings=item["embeddings"], n_results=n + 1, where=where)
    out = []
    for i, d, m in zip(res["ids"][0], res["distances"][0], res["metadatas"][0]):
        if i != item_id:                                           # drop the item itself
            out.append((i, f"{1 - d:.0%} similar", m.get("cuisine")))  # explain the pick
    return out[:n]

print(more_like("food_017", where={"calories": {"$lte": 700}}))

tests = [("peanut noodle dish", "food_017"), ("cheesy tomato pizza", "food_018")]  # use 10–20 pairs
def recall_at_k(k):
    found = sum(expected in col.query(query_texts=[q], n_results=k)["ids"][0] for q, expected in tests)
    return found / len(tests)

print("recall@1:", recall_at_k(1), " recall@5:", recall_at_k(5))

Key takeaways

Why it matters
  • A number like “recall@5 went from 0.70 to 0.90” is the only reliable proof that a change helped. It also makes a strong line in a project README or résumé.
Mistake to avoid
  • Recommending the item the user is looking at (forgetting to drop it).
  • Judging quality from two or three hand-picked queries.
Remember
  • Recommend = filter by rule → rank by similarity → drop self → explain. Measure with recall@k before and after changes.

Similarity search and the three metrics: L2, dot product, cosine

⏱ ~8 min🧭 1 diagram💻 0 code cells🧠 3 recall Qs
In a nutshellSimilarity search finds the items most similar to a query. It needs a metric: L2 (Euclidean) distance = straight-line gap (lower = closer); dot product = similarity that grows with angle and length; cosine similarity = angle only (higher = closer), and cosine distance = 1 − cosine similarity. For unit-length (normalized) vectors, dot product = cosine.

💡 In plain words

L2 asks “how far apart are the two arrow tips?”. Cosine asks “do the arrows point the same way?”. Dot product asks “same way and how long are they?”.

➡ Leads to 1.6 Lab: similarity search by hand

L2 measures the gap between arrow tips; dot product and cosine look at the angle (cosine ignores the arrow lengths).

Similarity search is used in recommendation systems (similar movies), image and video retrieval, NLP (similar documents or sentences) and biometrics (face recognition). A distance function gives larger numbers for vectors that are farther apart; a similarity function gives larger numbers for vectors that are more alike. A vector has a length (magnitude, the L2 norm ‖a‖ = √(Σ aₖ²)) and a direction. In embeddings, direction usually encodes the meaning/topic; magnitude can reflect intensity, confidence or popularity.

2 · L2 distance: loop, then scipy

Every pair of the 4 “Bugs …” sentences gets one cell. Only 6 of the 16 cells are really needed.
def euclidean_distance_fn(vector1, vector2):
    squared_sum = sum((x - y) ** 2 for x, y in zip(vector1, vector2))
    return math.sqrt(squared_sum)

l2_dist_manual = np.zeros([4,4])
for i in range(embeddings.shape[0]):
    for j in range(embeddings.shape[0]):
        l2_dist_manual[i,j] = euclidean_distance_fn(embeddings[i], embeddings[j])

l2_dist_scipy = scipy.spatial.distance.cdist(embeddings, embeddings, 'euclidean')
np.allclose(l2_dist_manual, l2_dist_scipy)   # True

The matrix is symmetric (l2_dist_manual[0,1] == l2_dist_manual[1,0]) and the diagonal is 0. ★ Exercise 1 asks you to skip this repeated work: compute only the upper triangle (j > i) and copy it into the lower triangle.

3 · Dot product and dot-product distance

def dot_product_fn(vector1, vector2):
    return sum(x * y for x, y in zip(vector1, vector2))

dot_product_manual = np.empty([4,4])
for i in range(embeddings.shape[0]):
    for j in range(embeddings.shape[0]):
        dot_product_manual[i,j] = dot_product_fn(embeddings[i], embeddings[j])

dot_product_operator = embeddings @ embeddings.T        # matrix multiplication
np.allclose(dot_product_manual, dot_product_operator, atol=1e-05)
np.matmul(embeddings, embeddings.T)   # same; recommended for 2-D arrays
np.dot(embeddings, embeddings.T)      # same result

dot_product_distance = -dot_product_manual   # similarity -> distance

The diagonal of the dot-product matrix is not zero: a vector multiplied by itself gives its squared length. All dot-product distances may be negative — that is fine, smaller still means closer.

4 · Normalize, then cosine

# L2 norms (one length per row)
l2_norms = np.sqrt(np.sum(embeddings**2, axis=1))
l2_norms_reshaped = l2_norms.reshape(-1,1)          # shape (4, 1) so division broadcasts per row
normalized_embeddings_manual = embeddings/l2_norms_reshaped

Chroma DB filtering: metadata (where) and document content (where_document)

⏱ ~9 min🧭 1 diagram💻 1 code cell🧠 4 recall Qs
In a nutshellChroma has two filters. Metadata filtering uses where= with operators like $eq $ne $gt $gte $lt $lte $in $nin and logic $and / $or. Document filtering (also called full-text search) uses where_document= with $contains / $not_contains and is case-sensitive. Both work in .get(), .query() and .delete().

💡 In plain words

Metadata is the small label dictionary you store with each document, e.g. {"source": "langchain.com", "version": 0.1}. A filter keeps only the records whose labels (or text) match a rule. In a vector query the filter runs together with the similarity search, so you get “the most similar documents that also match the rule”.

Metadata filteringwhere$eq $ne (str, int, float) · $gt $gte $lt $lte (int, float) · $in $nin (lists) · $and $orLike a SQL WHERE clause, but more flexible and combinable with vector search

Two filter types, three methods. Both can be combined with each other and with a vector query.

    documents=[
        "This is a document about LangChain",
        "This is a reading about LlamaIndex",
        "This is a book about Python",
        "This is a document about pandas",
        "This is another document about LangChain"
    ],
    metadatas=[
        {"source": "langchain.com", "version": 0.1},
        {"source": "llamaindex.ai", "version": 0.2},
        {"source": "python.org", "version": 0.3},

    ],

collection.get(where={"source": {"$eq": "langchain.com"}})        # -> id1, id5
collection.get(where={"$and": [{"source": {"$eq": "langchain.com"}},
                               {"version": {"$lt": 0.3}}]})       # -> id1
collection.get(where={"$and": [{"source": {"$in": ["langchain.com", "llamaindex.ai"]}},
                               {"version": {"$lt": 0.3}}]})       # -> id1, id2
collection.get(where_document={"$contains": "pandas"})            # -> id4  ("Pandas" finds nothing!)
collection.get(where={"version": {"$gt": 0.1}},
               where_document={"$or": [{"$contains": "LangChain"},
                                       {"$contains": "Python"}]}) # -> id3, id5

These .get() calls do not use embeddings at all, so the results are the same with Gemini as in the reading. .get() returns 'embeddings': None by default (Lesson 2.1).

📝 Quiz fact No operator = $eq: where={"key": "value"} is the same as where={"key": {"$eq": "value"}}. $nin means “not in”. Document filtering is case-sensitive and is also called full-text search. Filters work in .query(), .get() and .delete().

Key takeaways

Why it matters
  • Filters fix bad semantic matches cheaply (Lesson 1.9 “polar bear” example) and let you restrict a RAG retriever to one source, version, department or user.
  • The same where syntax is used to delete records (collection.delete(where=…)) — see Lesson 2.1.
Common pitfalls
  • Using $gt / $lt on strings — they work on int and float only.
  • Searching "Pandas" when the text says “pandas”: no result (case-sensitive).
  • Putting $contains in where instead of where_document.
  • Writing two conditions in one dict without $and — combine several conditions with $and / $or and a list.
Remember
  • where → metadata. where_document → text. $in / $nin → lists. $and / $or → combine.

Vector index and HNSW in Chroma DB: similarity search with configuration and filters

⏱ ~10 min🧭 1 diagram💻 1 code cell🧠 4 recall Qs
In a nutshellBrute force compares the query with every vector — slow at scale. A vector index organizes vectors so search only looks at a small subset. HNSW (Hierarchical Navigable Small World) is a multi-layer graph for approximate nearest-neighbour (ANN) search and the only index in Chroma. You set it with the "hnsw" key when you create a collection: space, ef_search, ef_construction, max_neighbors.

💡 In plain words

Think of a map with motorways, main roads and small streets. You start on the motorway (top layer, few points), get close to the destination, then take smaller roads (lower layers) until you reach the exact street (bottom layer, all vectors). It is approximate: very close to exact, but much faster.

HNSW: start at the sparse top layer, move towards the query, drop down a layer, repeat. Most of the data is never visited.

# Chroma embedding function backed by Gemini (replaces SentenceTransformerEmbeddingFunction("all-MiniLM-L6-v2"))
import os
os.environ.setdefault("ANONYMIZED_TELEMETRY", "False")
from chromadb import Documents, EmbeddingFunction, Embeddings
from langchain_google_genai import GoogleGenerativeAIEmbeddings

class GeminiEmbeddingFunction(EmbeddingFunction):
    def __init__(self, model: str = "models/gemini-embedding-2"):
        self.model = model
        self._emb = GoogleGenerativeAIEmbeddings(model=model)   # key read from GOOGLE_API_KEY

    def __call__(self, input: Documents) -> Embeddings:
        texts = list(input)
        out = []
        for i in range(0, len(texts), 100):              # free tier: <= 100 texts per call
            out += self._emb.embed_documents(texts[i:i + 100])
        return out

    @staticmethod
    def name() -> str:
        return "gemini"

    def get_config(self):
        return {"model": self.model}

    @staticmethod
    def build_from_config(config):
        return GeminiEmbeddingFunction(config.get("model", "models/gemini-embedding-2"))

name(), get_config() and build_from_config() let Chroma save which embedding function a collection uses and rebuild it later (important for a PersistentClient). The loop sends at most 100 texts per call (free-tier limit).

import chromadb
from chromadb.utils import embedding_functions
from gemini_ef import GeminiEmbeddingFunction  # Colab: Gemini embeddings

def perform_similarity_search(collection, all_items):
    try:
        query_term = ["red", "fresh"]                 # lab first uses query_term = "apple"
        results = collection.query(
            query_texts=query_term,
            n_results=3  # Retrieve top 3 results
        )
        if not results or not results['ids'] or len(results['ids'][0]) == 0:
            print(f'No documents found similar to "{query_term}"')
            return
        for q in range(len(query_term)):
            print(f'Top 3 similar documents to "{query_term[q]}":')
            for i in range(min(3, len(results['ids'][q]))):
                doc_id = results['ids'][q][i]          # Get ID from 'ids' array
                score = results['distances'][q][i]     # Get score from 'distances' array
                text = results['documents'][q][i]
                print(f' - ID: {doc_id}, Text: "{text}", Score: {score:.4f}')
    except Exception as error:
        print(f"Error in similarity search: {error}")

Essential Chroma DB operations: collections and CRUD

⏱ ~10 min🧭 1 diagram💻 1 code cell🧠 4 recall Qs
In a nutshellA client (chromadb.Client()) holds collections. You create, get and modify collections, then run CRUD on records: add, get, update, delete. get() hides embeddings by default; update() re-embeds in the background. The embedding model and the distance metric can’t be changed later — you must clone the collection.
🎯 After this lesson you can
  • create a collection with metadata and an embedding function
  • connect to an existing collection and rename it with modify
  • add, read, update and delete records, also with where filters
  • set the distance function with "hnsw": {"space": …}
  • say what cannot be modified and what to do instead
💡 In plain words

CRUD = Create, Read, Update, Delete — the four basic things you do with stored data. In Chroma every record needs a unique id. You give it text and metadata; Chroma creates the vector. When you change the text with update, Chroma creates a new vector for you.

    metadata={"description": "A collection for storing user data"},

        "embedding_function": ef,

# Create
collection.add(
    documents=["This is a document about LangChain",
               "This is a document about LlamaIndex"],
    metadatas=[{"source": "langchain.com", "version": "0.2"},
               {"source": "llamaindex.ai", "version": "0.12"}],
    ids=["id1", "id2"]                       # one id per document
)
# Read
results = collection.get()                       # all records (a Python dict)
results = collection.get(ids=["id1"])            # by id

# Update (Chroma re-embeds the new text in the background)
collection.update(ids=["id1"],
                  metadatas=[{"source": "langchain.com", "version": "0.3"}],
                  documents=["This an updated document about LangChain"])
# Delete
collection.delete(ids=["id1"])
collection.delete(where={"source": "llamaindex.ai"})
collection.delete(ids=["id1"], where={"version": "1.0"})   # ids and filter together

Key takeaways

Why it matters

  • Concluding that no embeddings were saved because get() shows None.

How vector databases power RAG

⏱ ~12 min🧭 1 diagram💻 1 code cell🧠 5 recall Qs
In a nutshellRAG (Retrieval-Augmented Generation) gives an LLM fresh, relevant text from outside sources before it answers, so answers are grounded and hallucinations drop. A vector database does the core RAG work: it embeds documents and prompts, stores the vectors, retrieves the best matches and supplies the text for the prompt. Chunking, prompt augmentation and the LLM call happen outside the database — frameworks like LangChain and LlamaIndex fill those gaps.

  • name the 4 common pitfalls and their fixes
  • list what vector databases don’t handle and what fills the gap
💡 In plain words

An LLM only knows what it saw in training. RAG is like an open-book exam: before answering, the system looks up the right pages (retrieval) and puts them next to the question (augmentation). The vector database is the fast librarian that finds those pages by meaning.

➡ Leads to 2.4 Project: food recommendation system

📝 Quiz fact RAG = a framework that enhances language models by retrieving relevant information from external sources and using it to generate more accurate, grounded responses, reducing hallucinations.

Three problems RAG solves

ProblemWhat it meansHow RAG helps
Limited context windowYou can’t paste all your documents into one prompt.Only the few most relevant chunks go into the prompt.
Knowledge is frozenThe model knows nothing after its training date or about your private data.Retrieval brings in current and private information.
HallucinationsThe model may invent facts that sound right.The answer is grounded in retrieved source text.

The 8-step RAG pipeline

The 8-step RAG pipeline from the cheat sheet. The vector database embeds, stores, retrieves and supplies the text; chunking, prompt augmentation and the LLM call happen outside it.
  1. Relevant source documents are provided and possibly split into smaller chunks.
  2. The documents or chunks are embedded.
  3. Sources and embeddings are stored in a vector database such as Chroma DB.
  4. The user’s prompt is received.
  5. The prompt is embedded (same model!).
  6. The retriever selects the chunks that best match the prompt.
  7. Retrieved text + original prompt = augmented prompt.
  8. The augmented prompt goes to the LLM → context-aware response.

📝 Quiz fact A vector database can handle: embedding documents and prompts (steps 2 and 5), storing embeddings (3), retrieving the best matches (6) and supplying retrieved content for augmentation. Steps 2 and 5 can also be done externally — then the DB only stores and retrieves.

Why let the vector database do these steps?

ReasonDetails
1. Prevents critical mistakesNo accidental use of different embedding models for documents and prompts; no wrong links between embeddings and their source documents.
2. Faster, cleaner developmentFewer moving parts and less custom code → simpler code that is faster to build and debug.
3. PerformanceBuilt for high-speed, scalable semantic search with advanced indexing (HNSW in Chroma). Home-made code rarely matches it.

Common pitfalls and best practices

PitfallBest practice
Different embedding models for documents and queries → retrieval breaksUse the same model everywhere (a vector DB with an embedding function does this automatically).
Chunks too long or too shortChoose a size long enough to keep the meaning, short enough to skip irrelevant text.
Not re-embedding after changing the embedding model or distance metricRe-embed. In Chroma this can’t be done on an existing collection → clone the collection.
Assuming the retrieved result is always the bestTest your results; a little tuning makes a big difference.

What vector databases don’t handle

  • Chunking — usually done before the data enters the database.
  • Extra retrieval logic such as advanced filtering and re-ranking may need extra tools.
  • Prompt augmentation — usually done outside the database.
  • LLM integration — not built into most vector databases.

RAG frameworks (LangChain, LlamaIndex) wrap around the vector database, add structure, simplify development and deployment, and connect all the pieces from document preparation to the final answer.

P2 · Similarity by hand: L2, dot product, cosine in NumPy

⏱ ~4 min🗺 1 diagram💻 1 code cell🧩 skill 2
In a nutshellOne small function returns all three scores for a query against a matrix of vectors; one more ranks them. L2 is a distance (smaller = closer), dot product and cosine are similarities (bigger = closer). Dot product rewards long vectors, cosine ignores length, and after normalising every row, dot product = cosine and L2 ranks the same way.
🎯 Use it when
  • A Chroma score looks strange and you want to check it yourself.
  • You must explain why two metrics give different top-1 results.
💡 In plain words

Two arrows from the same point: L2 measures the gap between their tips, cosine measures the angle between them, dot product mixes the angle with how long the arrows are.

📓 Built from: 1.6 (manual + scipy L2, @ for dot products, row normalisation, Exercise 3); cheat sheet in 1.5; TenderYar Cell 3 in C.2.

Why the metric matters: B points the same way as q but is 5× longer. Dot product picks B, L2 punishes it, cosine calls it a tie with A.
💻 Cell · scores() + rank() — the reusable by-hand checker
import numpy as np

def scores(q, D):
    q, D = np.asarray(q, float), np.asarray(D, float)
    l2  = np.linalg.norm(D - q, axis=1)                         # smaller = closer
    dot = D @ q                                                 # bigger  = closer
    cos = dot / (np.linalg.norm(D, axis=1) * np.linalg.norm(q)) # bigger  = closer, ignores length
    return {"l2": l2, "dot": dot, "cos": cos}

def rank(q, D, metric="cos"):
    s = scores(q, D)[metric]
    return list(np.argsort(s if metric == "l2" else -s))       # best first

docs = {"A": [1, 1], "B": [5, 5], "C": [1, 0.8]}
q, D = [1, 1], list(docs.values())
for m, v in scores(q, D).items(): print(m, np.round(v, 3))
for m in ["l2", "dot", "cos"]: print(m, [list(docs)[i] for i in rank(q, D, m)])

Dn = np.asarray(D, float) / np.linalg.norm(D, axis=1, keepdims=True)
qn = np.asarray(q, float) / np.linalg.norm(q)
print("normalised dot == cos:", np.allclose(Dn @ qn, scores(q, D)["cos"]))
print("normalised l2 rank:", [list(docs)[i] for i in rank(qn, Dn, "l2")])

P5 · Pick the space + HNSW knobs; turn a distance into a similarity

⏱ ~6 min🗺 1 diagram💻 3 code cells🧩 skill 3
In a nutshellChoose the metric once, at creation: configuration={"hnsw": {"space": "cosine"}} (or the older metadata={"hnsw:space": "cosine"}). The default is l2. On unit-length vectors all three spaces give the same ranking; only the distance numbers differ, so convert them the right way before you show a "similarity". After creation you can still tune ef_search (speed ↔ recall); space and ef_construction are locked — change them with a clone (P3).
🎯 Use it when
  • You create a new collection and must pick a metric.
  • You print scores to users or apply a "minimum similarity" threshold.
  • Search feels slow, or misses neighbours on a large collection.
💡 In plain words

The space is the ruler you measure with; HNSW is the road map that lets you skip most houses. ef_search is how many houses you peek into on the way: more peeks, better answer, slower walk.

P6 · Recommender: filter by rule, rank by similarity, drop the item itself, explain the pick

⏱ ~6 min🗺 1 diagram💻 2 code cells🧩 skills 6, 7, 8
In a nutshell"More like this" = take the stored vector of the item the user likes (get(ids=[…], include=["embeddings"])), query with it plus a where rule, ask for a few extra results, then drop the item itself and same-name duplicates and attach a short reason (shared ingredients, same cuisine, calories). 🎯 Use it when

def recommend(item_id, k=3, where=None):
    me = coll.get(ids=[item_id], include=["embeddings", "metadatas"])
    vec, mine = me["embeddings"][0], me["metadatas"][0]
    r = coll.query(query_embeddings=[vec], n_results=k + 3, where=where,
                   include=["metadatas", "distances"])
    out, seen_names = [], {mine["name"]}
    for i, m, d in zip(r["ids"][0], r["metadatas"][0], r["distances"][0]):
        if i == item_id or m["name"] in seen_names: continue      # drop self + same-name duplicates
        seen_names.add(m["name"])
        shared = sorted(set(mine["ingredients"].split(", ")) & set(m["ingredients"].split(", ")))
        why = (["shares " + ", ".join(shared[:3])] if shared else []) \
            + (["same cuisine"] if m["cuisine"] == mine["cuisine"] else []) + [f"{m['calories']} kcal"]
        out.append((i, m["name"], round(1 - d, 3), "; ".join(why)))
    return out[:k]

def retrieve(question, k=3, max_dist=0.70, where=None):
    r = coll.query(query_texts=[question], n_results=k, where=where,
                   include=["documents", "metadatas", "distances"])
    hits = [{"id": i, "doc": d, "meta": m, "dist": round(x, 3)}
            for i, d, m, x in zip(r["ids"][0], r["documents"][0], r["metadatas"][0], r["distances"][0])]
    kept = [h for h in hits if h["dist"] <= max_dist]                 # weak hits never reach the LLM
    return kept, hits

import re
def offline_answer(question, kept):                                   # deterministic stand-in for the LLM
    if not kept: return "NOT_FOUND"
    top = kept[0]
    return f"Try {top['meta']['name']} [{top['id']}] ({top['meta']['calories']} kcal)."

def check_citations(answer, kept):
    cited = set(re.findall(r"\[([^\]]+)\]", answer)); allowed = {h["id"] for h in kept}
    return {"cited": sorted(cited), "unknown": sorted(cited - allowed),
            "ok": answer == "NOT_FOUND" or (bool(cited) and cited <= allowed)}

def rag(question, llm=offline_answer, **kw):

    if not kept: return {"answer": "NOT_FOUND", "sources": [], "cited": [], "unknown": [], "ok": True}   # no LLM call
    ans = llm(question, kept)
    return {"answer": ans, "sources": [h["id"] for h in kept], **check_citations(ans, kept)}

def recall_at(coll, pairs, k=5):

Similarity by hand, then by machine

⏱ ~15 min💻 Cells 3–4📏 metrics📖 re-uses W1 · similarity metrics · W1 lab · by hand
In a nutshellBefore trusting a vector database, compute what it computes. Three tiny vectors show the trap: «آسفالت ×۲» points in the same direction as «آسفالت» (cosine = 1.000) but is far away in L2 (2.236) and has double the dot product (10 vs 5). Dot product rewards length, so normalise first or use cosine. Then rank real models: 20 Persian query–passage pairs, each query must find its own passage → recall@1, recall@5 and milliseconds per embedding.
🎯 Steps
  • Compute dot, cosine and L2 for three 3-D vectors with NumPy (Cell 3).
  • Run bench() on data/embed_pairs.jsonl for offline hash, Gemini embedding-2, Tooka-SBERT and bge-m3 (Cell 4).
  • Pick the default model and write why in RESULTS.md.
💡 In plain words

Cosine asks “do these point the same way?”, L2 asks “how far apart are the tips?”, dot asks “how much does one push along the other?”. For meaning you want the first question.

Three ways to say “close”

💻 Cell 3 · three tiny vectors: cosine vs dot vs L2
import numpy as np
V = {"آسفالت": np.array([1., 2., 0.]), "آسفالت ×۲": np.array([2., 4., 0.]), "آب": np.array([0., 1., 2.])}
q = V["آسفالت"]
for k, v in V.items():
    cos = q @ v / (np.linalg.norm(q) * np.linalg.norm(v))
    print(f"{k:12s} dot={q @ v:5.1f}  cos={cos:.3f}  L2={np.linalg.norm(q - v):.3f}")
# same direction, double length: cosine 1.000 but L2 2.236 and dot 10 → normalise before you use dot

🌱 Beyond the course · pre-filter vs post-filter in vector databases

Chroma applies where and then searches among the survivors. Some engines search first and filter afterwards (post-filter), which can return fewer than k results when the filter is selective. Matching: “which tenders should my company bid on?”

⏱ ~20 min💻 Cells 10–11🎯 recommender📖 re-uses W2 · Food recommendation project · W2 · Employee records lab
In a nutshellThe recommender has two stages, like the food project (filter by diet, then rank by taste). Stage 1 — hard rules (hard_filter): province in the company's area, category in its fields, grade good enough (Iranian rank 1 is best, so rank g may bid when g ≤ required level), deadline not passed, bond ≤ the company's cap. Every rule writes a Persian reason. Stage 2 — soft score (soft_score) for the survivors: 0.6·similarity + 0.2·deadline_room + 0.2·bond_fit, where deadline_room = min(days, 30)/30 and bond_fit = 1 − bond/cap. We compare three variants on the rule-labelled gold set with precision@5.

A good assistant first throws away tenders you cannot win (wrong province, grade too low, bond too big) and tells you why. Then it sorts the rest: similar work first, with enough time to prepare and a bond you can easily pay.

🔍 Why “full” beats “filter” for Zagros

With filter the order is pure similarity: S024 (0.3724, deadline 1405/08/22) and S028 (0.3233, deadline 1405/08/21) sit at ranks 1 and 3. Both pass every hard rule, but they leave only 2 and 1 days — no real company can prepare a bid that fast, so the gold labels (which require ≥ 7 days) say “no”. In full, deadline_room is 2/30 and 1/30 for them, so they fall to ranks 6 and 7 (0.3443, 0.3006) and the 5 gold tenders move up: 0.6 → 1.0. Semantic-only is worst (0.2): it puts S014 (Mazandaran) and S050 (Khuzestan) in the top 5, which Zagros cannot bid on.

⚠️ Three traps in this step
  • Grade direction. In Iran, rank 1 is the best grade. “Required rank 4” accepts companies with rank 1–4, so the test is company ≤ required, not ≥. A flipped sign silently keeps the wrong tenders.
  • precision@5 has a ceiling. Shomal has only 4 tenders that pass the rules (and 4 gold), so the best possible precision@5 is 4/5 = 0.8 — the 0.8 is a perfect score here, not a miss. Report recall too, or use k = min(5, #relevant).
  • Fixed “today”. EVAL_TODAY = 1405/08/20 keeps the evaluation reproducible. A real app must use today's Jalali date, or every deadline slowly becomes “passed”.
💡 The weights are a guess — treat them like a hyper-parameter

0.6 / 0.2 / 0.2 were chosen once and not tuned. If you change them, check all three profiles, and keep a few profiles that you do not look at while tuning — otherwise you fit the weights to your own test set.

🌱 Beyond the course · learning to rank and re-rankers

With real user feedback (“bid” / “skip”) you can learn the weights (logistic regression on sim, days, bond ratio) instead of guessing them. A cross-encoder re-ranker (for example bge-reranker) can replace the cosine sim for the top 20: slower, but it reads profile and tender together and usually ranks better than two separate embeddings.

One-page cheat sheet

Vector DB in one line

Stores vectors (embeddings) + documents + metadata and finds the most similar ones fast. Full CRUD, unlike a vector library (Faiss) that only holds an index in memory.

Vector vs traditional

Traditional = exact match on structured rows (SQL). Vector = similarity on unstructured data (text, images, audio). Many traditional DBs now add vector search (vectors as BLOBs).

DB types

Dedicated vector DBs (Faiss, Annoy, Milvus; Chroma in the labs) · DBs that support vector search (SingleStore, PostgreSQL, RedisAI, Cassandra, Elasticsearch, MySQL, MongoDB; vectors as BLOBs/arrays/UDTs) · other types: distributed, graph-based, time-series.

3 metrics

L2 = straight-line distance (smaller = closer) · dot = a @ b (bigger = closer) · cosine = angle only (bigger = closer); cosine distance = 1 − cos. Normalized vectors → dot = cosine.

By hand (NumPy)

embeddings = np.array(model.embed_documents(documents)) · scipy.spatial.distance.cdist · embeddings @ embeddings.T · np.linalg.norm(..., axis=1).reshape(-1,1) · 1 - cos.

Create

CRUD

add · get(ids=…) / get(where=…) · update (re-embeds documents) · upsert · delete(ids=…) / delete(where=…) · modify = name/metadata only (not model/metric → clone).

Query

Filters

HNSW

Chroma’s only index; layered graph for approximate NN search. Params: space (l2 default, ip, cosine), ef_search, ef_construction, max_neighbors.
