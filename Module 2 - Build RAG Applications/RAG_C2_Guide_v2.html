RAG in one page: two phases and the knobs you can turn

⏱ ~7 min🧭 1 diagram💻 0 code cells🧠 3 recall Qs
In a nutshellEvery RAG app in this course — LangChain or LlamaIndex, notebook or Gradio — has the same two phases. Indexing (once): load → split → embed → store. Query (every question): embed the question → retrieve the top-k chunks → put them in the prompt → the LLM answers. When an answer is bad, one of a handful of knobs is usually the cause.
🎯 After this lesson you can
  • Say which work happens once (indexing) and which happens per question (query).
  • Trace one question through all 8 steps of the course diagram.
  • Pick the knob to change for a given symptom.
💡 In plain words

Indexing is building a library catalogue once. The query phase is a librarian who uses that catalogue for every visitor, brings the 3 best pages, and a writer (the LLM) answers using only those pages.

➡ Leads to 1.1 What RAG is

Indexing builds the searchable library once; the query phase uses it for every question. Green = retrieval side, purple = LLM side.

The course's running example: a company chatbot that answers "What is our mobile policy?" from the company's policy document. The numbers are the slide's 3-number toy vectors; real embeddings have hundreds or thousands of numbers.

Debug in this order — most bad answers are retrieval problems

  2. Split well? Print the number of chunks and one chunk. Does a chunk hold one complete idea?

  4. Only then change the prompt, the chain type or the LLM.

Key takeaways

Why it matters
  • Every later topic — Gradio front-ends, LlamaIndex, vector databases, agents — plugs into these two phases. If you can draw them, you can read any RAG codebase.
Common pitfalls
  • Rebuilding the index for every question (slow, costly).
  • Changing the embedding model but keeping the old vector store.
  • Rewriting the prompt when the retriever never found the right chunk.
Remember
  • Index once, query many times. Same embedding model on both sides. Check retrieval before you blame the LLM.
🧠 Active recall: answer before you open
Which steps run for every question?
Embed the question, retrieve top-k, augment the prompt, generate (steps 4–8). Load, split, embed chunks and store run once.
The answer says "I don't know" but the fact is in the PDF. First two knobs to check?
k (the right chunk may be just outside the top-k) and chunk_size/overlap (the fact may be cut in half). Test the retriever alone first.
You switch to a new embedding model. What else must you do?
Re-embed all chunks and rebuild the vector store; old and new vectors are not comparable.

Week 1 · Lesson 1.1

What RAG is and why LLMs need it

⏱ ~5 min🧭 1 diagram💻 0 code cells🧠 3 recall Qs
In a nutshellRAG = retrieve relevant facts from your own knowledge base, add them to the prompt, then let the LLM generate. It makes answers current, domain-specific and grounded, without retraining the model.
🎯 After this lesson you can
  • Define RAG in one sentence.
  • List the problems of a pre-trained LLM that RAG solves.
  • Explain why RAG updates the data store instead of retraining the model.
💡 In plain words

A student in an open-book exam: the brain (LLM) writes the answer, but first the student looks up the right page in the book (knowledge base).

➡ Leads to 1.2 The RAG process

RAG adds one step before generation: look the facts up first.

Retrieval-Augmented Generation (RAG) is an AI framework that optimizes the output of an LLM. It keeps the LLM's language skills but feeds it relevant facts from an external knowledge source (a "content store" or "knowledge base") at question time. The model's weights do not change: there is no retraining.

Problem of a pre-trained LLMWhat happensHow RAG helps
Out-of-date knowledgeTraining data stops at a date, so the model may give an old fact (e.g. the planet with the most moons)Update the data store, not the model. New facts are retrieved at question time.
No domain or private dataIt has never seen your company's mobile policy or other confidential documentsIndex your own documents; the retriever finds the relevant part
No sourceThe answer sounds sure but cannot be checkedThe answer is grounded in retrieved text that you can show
HallucinationThe model fills gaps with plausible-sounding textA prompt that says "answer only from the context" + relevant context lowers the risk
Importance of RAG (slide)
  • Pre-trained LLMs face challenges with specific, private or new information.
  • They perform well on general tasks.
  • So it is advantageous to add relevant knowledge sources instead of building a new model.
  • 📝 Quiz fact To fix out-of-date answers, RAG augments the data store with updated information. It does not continuously retrain the model, increase parameters or switch to a bigger model.
  • 📝 Quiz fact For the "planet with the most moons" question, RAG instructs the model to consult the content store before generating a response, so the answer is based on current information.
  • 📝 Quiz fact RAG gives domain-specific, accurate answers by using external knowledge sources to augment the user's prompt — not by retraining or by adding tokens.

The course's running example is a company chatbot. A general LLM cannot answer "What is our mobile policy?" because the policy is private. A RAG chatbot searches the company's policy documents, finds the mobile-policy chunk and gives it to the LLM together with the question.

Key takeaways

Why it matters
  • Most real company chatbots (HR, IT, legal, product docs) are RAG systems. Fine-tuning a model for every policy change is slow and expensive; updating a document store is cheap.
Common pitfalls
  • Saying RAG "retrains" or "fine-tunes" the model. It does not touch the weights.
  • Choosing "use a bigger model" or "increase parameters" in quiz options about out-of-date answers. The RAG answer is always "update/consult the data store".
Remember
  • RAG = Retrieval + Augmentation + Generation. External knowledge goes into the prompt, never into the weights.
🧠 Active recall: answer before you open
Why does a pre-trained LLM give out-of-date answers?
Its knowledge is frozen at training time. It cannot know facts that appeared later.
How does RAG keep answers current?
By updating (augmenting) the data store; the retriever brings new facts into the prompt at question time.
Does RAG change the model weights?
No. It only changes what goes into the prompt.

⏱ ~6 min🧭 2 diagrams💻 0 code cells🧠 3 recall Qs
In a nutshellTwo components: the retriever (find relevant chunks) and the generator (LLM writes the answer). Four steps: Text Embedding → Retrieval → Augmented Query Creation → Model Generation.
🎯 After this lesson you can
  • Draw the 8-step RAG pipeline from memory.
  • Name the two components and the four summary steps.
  • Define an augmented prompt and explain why documents are split.
💡 In plain words

Indexing is filling a library catalogue once. Querying is asking the librarian, who checks the catalogue, brings 3 books, and the writer answers using them.

➡ Leads to 1.3 Prompt & context encoding

Indexing phase (done once, before any question): steps 1–3.
Query phase (every question): steps 4–8. The same embedding model must be used in steps 2 and 5.

The course draws RAG as an 8-step pipeline. It has two main components:

ComponentJobSteps
RetrieverEncodes the question and matches the prompt vector with the vectors in the knowledge base to fetch relevant chunks5–7
GeneratorThe LLM. Uses the retrieved information to write the answer in natural language8

The official summary compresses the same pipeline into four steps:

# in course diagramStepWhat happens
1Text EmbeddingPrompts and knowledge-base documents become high-dimensional vectors (embedding models such as BERT or GPT)
2RetrievalThe query vector is matched with similar vectors in the knowledge base
3Augmented Query CreationRetrieved content + user prompt = the augmented prompt
4Model GenerationThe LLM answers from the augmented query, using the knowledge-base content
  • 📝 Quiz fact The retriever's role: to match the prompt vector with vectors in the knowledge base. (Converting the prompt to a vector is encoding; writing the answer is the generator.)
  • 📝 Quiz fact An augmented prompt = a combination of the original prompt and the retrieved relevant data from the vector store.
  • 📝 Quiz fact Large documents: a document splitter splits the document into smaller, manageable chunks; each chunk is embedded and stored separately.
  • 📝 Quiz fact For accurate, specific chatbot answers, focus on keeping the knowledge base up-to-date and well-organized for efficient retrieval.
  • 📝 Quiz fact The retrieval component improves accuracy because it augments the user's prompt with relevant, up-to-date information from a content store.
Recap from the slides
  • RAG helps generate responses where a chatbot would struggle with a specific domain, for example a company's mobile policy.
  • The chatbot encodes the question, breaks the documents into chunks, converts the chunks into high-dimensional vectors, and uses a distance metric to select the chunks closest to the question from the knowledge base.

Key takeaways

Why it matters
  • Every RAG bug sits in one step. Wrong answer? Check retrieval first (did the right chunk come back?), then the prompt, then the model.
Common pitfalls
  • Mixing up roles: the retriever matches vectors; it does not generate text and does not embed the documents.
  • Forgetting that documents are split into chunks before embedding; one vector per huge document retrieves badly.
  • Thinking the indexing phase runs for each question. It runs once (or when documents change).

Prompt & context encoding: from tokens to vectors

⏱ ~6 min🧭 2 diagrams💻 3 code cells🧠 3 recall Qs
In a nutshellText → tokenizer (tokens + IDs) → neural network (token IDs → vectors) → vector averaging (one vector per prompt or chunk). Chunk vectors are stored as the knowledge base.
🎯 After this lesson you can

  • Describe how chunks become a knowledge base (context encoding).

💡 In plain words

Each word gets a GPS coordinate in "meaning space"; the average of a sentence's word coordinates is the sentence's address.

➡ Leads to 1.4 Similarity search & top-K

Question encoder (prompt encoding). The context encoder does the same for every chunk.

An LLM and a vector database work with numbers, not text. Encoding turns text into a vector (a list of numbers, also called an embedding). Texts with similar meaning get vectors that point in similar directions.

  1. Tokenization: a tokenizer splits text into tokens (words or word pieces) and gives each token a unique number, its token ID.
  2. Token embedding: a neural network (the embedding model, e.g. BERT or GPT-style) takes the token IDs and outputs one numeric vector per token.
  3. Vector averaging: the token vectors are averaged into one vector for the whole prompt: q = (1/N) Σ token_vectorᵢ.
  • 📝 Quiz fact Tokenization splits text into tokens and assigns numerical IDs to those tokens.
  • 📝 Quiz fact The neural network in the embedding step transforms token IDs into numeric vectors.
  • 📝 Quiz fact Company mobile-policy chatbot: RAG embeds the policy into high-dimensional vectors and uses them to retrieve relevant information — not rules, not retraining.

Context encoding: building the knowledge base

Slide example: policy text split into chunks 0–6; each chunk becomes a row of the knowledge base (illustrative numbers).

🔍 Deeper look: what an embedding really is, and why both sides need the same model

What the numbers mean. An embedding model is trained so that texts with similar meaning get vectors that point in similar directions — "phone rules" lands close to "mobile policy" even though no word matches. No single number is a readable feature; the meaning is in the position of the vector relative to the others.

Fixed length. One model always returns vectors of the same length, whether the text is 3 words or 3 pages (e.g. all-MiniLM-L6-v2 → 384 numbers). Check yours with len(vec). Averaging (pooling) is how a variable number of token vectors becomes one fixed-length vector.

Why both sides need the same model. Each model has its own "coordinate system". A question embedded with model A and chunks embedded with model B are like a GPS position on one map and a street address on another: the numbers can be compared mathematically, but the result is meaningless.

Similarity search, top-K and response generation

⏱ ~6 min🧭 2 diagrams💻 3 code cells🧠 3 recall Qs
In a nutshellThe retriever scores every chunk against the question: dot product (magnitude + direction) or cosine (direction only). It keeps the top K (e.g. K = 3), adds them to the prompt, and the LLM generates the answer.
🎯 After this lesson you can

  • Pick the top-K chunks from a list of distances.
  • Run similarity_search(q, k=3) on a Chroma store.
💡 In plain words

Dot product asks "how strongly and in what direction?"; cosine only asks "in what direction?". Top-K is "bring me the 3 closest books".

➡ Leads to 1.5 RAG vs long context

Slide question: "Which of c1, c2 is more similar to q?" The answer depends on the metric.
MetricFormulaMeasuresBigger = more similar?
Dot productq·c = Σ qᵢ × cᵢDirection and magnitude (length)Yes
Cosine similaritycos φ = q·c / (|q| |c|)Direction only (angle between vectors), range −1…1Yes

📝 Quiz fact Official summary: distance metrics measure similarity using dot product (magnitude-based) or cosine similarity (direction-based).

Select the top K chunks

The retriever compares the question vector with every chunk vector and keeps the K most similar. The slide uses distances (smaller = closer) and argsort:

Distance to question0.650.710.050.89…0.15

δ = argsort(distances)[:K] with K = 3 → chunks 2, 6, 0. Chunk 2 (distance 0.05) says "Our mobile policy allows employees to use personal devices for work": exactly the context the question "What is your mobile policy?" needs.

🔍 Deeper look: dot product vs cosine, worked by hand

Work it out by hand once with 2-number vectors — the same situation as the slide (c1 is long but points elsewhere; c2 is short but points the same way as q).

q = (4, 3)c1 = (1, 5)c2 = (2, 1.5)
Length ‖v‖√(16+9) = 5√26 ≈ 5.10√(4+2.25) = 2.5
Dot product with q—4·1 + 3·5 = 19 ✅ wins4·2 + 3·1.5 = 12.5
Cosine with q—19 / (5 · 5.10) ≈ 0.7512.5 / (5 · 2.5) = 1.00 ✅ wins
Cosine distance 1 − cos—0.250.00 ✅ (smaller wins)

Reading it. The dot product rewards c1 for being long; cosine sees that c2 points in exactly the same direction as q, so it is the better topic match. That is why cosine (direction only) is the usual choice for text: a vector's length should not decide relevance.

  • Normalised vectors: many embedding models return vectors of length 1. Then dot product = cosine, and the choice no longer matters.
  • Similarity vs distance in code: similarity_search_with_score() on Chroma returns a distance by default (L2), so lower = better. LlamaIndex's node.score is a similarity, so higher = better. Always check which one you are reading before setting a threshold.

Key takeaways

Why it matters
  • K is a real trade-off: too small and you miss the answer; too large and you add noise, cost and latency.
  • Cosine is the usual default because chunk length should not decide relevance.
Common pitfalls
  • Mixing similarity and distance: with a distance, the smallest value wins (0.05 beats 0.89).
  • Saying cosine depends on vector length. It does not; the dot product does.
  • Thinking argsort returns values. It returns the indices (chunk IDs) in order.
Remember
  • Dot = magnitude-based. Cosine = direction-based. Top-K = the K nearest chunks.

Q1. What is the primary function of the retriever component in the Retrieval Augmented Generation (RAG) process?

✅ Answer A. The retriever's role is to match the prompt vector with vectors in the knowledge base to retrieve relevant information.

Q2. How does the RAG process address the challenge of large language models providing out-of-date information?

✅ Answer B. RAG addresses this challenge by augmenting the data store with updated information, ensuring responses are current. Retraining (D) is the expensive thing RAG avoids.

Q3. Imagine a user asks a large language model about the planet with the most moons. How does the RAG framework improve the accuracy of the response?

✅ Answer C. The RAG framework instructs the model to consult the content store, ensuring the response is based on the most current information.

Q4. How does RAG handle extremely large documents during the embedding process?

✅ Answer D. Document splitters split large documents into chunks, which are then individually embedded and stored in the vector store.

Q5. What is an augmented prompt in the RAG system?

✅ Answer B. An augmented prompt is a combination of the user's original prompt and retrieved relevant data from the vector store. It is not a list of vectors (C): the LLM receives text.

📝 Graded Quiz: Introduction to RAG

Q1. How does the RAG process ensure more accurate responses when dealing with specialized domain queries?

✅ Answer D. RAG uses external knowledge sources to provide more domain-specific and accurate responses.

Q2. Marina is using a large language model to answer a question about the planet with the most moons. What step should she take to ensure the response is accurate and up-to-date?

✅ Answer C. In the RAG framework, retrieving the latest information from a reliable source ensures the response is accurate and up-to-date. Pre-trained parameters (B) are frozen at a cut-off date.

Q3. How does the retrieval component improve the accuracy of large language models?

✅ Answer A. The retrieval component augments the model's responses by accessing relevant and current information from a content store.

Q4. Alex is developing a chatbot to answer questions about company policies. Which aspect of the RAG process should he focus on to ensure the chatbot provides accurate and specific responses?

✅ Answer D. An organized and current knowledge base is crucial for the RAG process, as it allows for the retrieval of relevant information and the assurance of accurate responses.

Q5. Imagine you are developing a chatbot for a company with a complex mobile policy. How does the Retrieval Augmented Generation (RAG) process ensure the chatbot provides accurate and domain-specific responses to questions about the company's mobile policy?

✅ Answer C. RAG uses embeddings to represent the company's policy and retrieve relevant context for accurate responses.

Q6. What is the role of neural networks in the embedding step of RAG?

✅ Answer C. Neural networks in embedding models take token IDs as inputs and produce numeric vectors as outputs. Converting text into tokens (D) is the tokenizer's job, not the neural network's.

✅ Answer D. A tokenizer splits text into tokens and assigns unique numerical IDs to each token. Vectors come later, from the embedding model.

🔍 Deeper look: what happens when the user clicks Submit

Every click on Submit runs one round trip:

  1. The browser sends the current values of the input components to the Gradio server (your Colab cell).
  2. Gradio converts them to Python values and calls fn(value1, value2, …).
  3. Whatever fn returns is converted back and shown in the output component(s).

Three practical consequences for RAG apps:

  • Code inside fn runs on every click. Loading the LLM, reading a PDF or building the vector store there makes each question slow and costly. Do one-time setup outside fn, or cache it (see P11).
  • Test fn on its own first. Call it in a normal cell, e.g. print(retriever_qa("file.pdf", "What is this about?")). If it works there, Gradio is only the window. Errors inside fn appear in the UI as a short "Error" — the full traceback is in the Colab cell output.
  • The app lives only while the cell runs. Stopping the cell, a runtime restart or a Colab timeout ends the app; re-run the cell and use the new link. demo.close() stops it cleanly before you launch a changed version.

Key takeaways

Why it matters
  • A RAG app is only useful when people can use it; Gradio gives a UI in a few lines.
  • Quiz questions test the order of the steps and the role of gr.Interface.
Common pitfalls
  • Saying gr.Interface defines the logic or launches the server — the function holds the logic and launch() starts the server.
  • In Colab, forgetting share=True → no link you can open.
Remember
  • gr.Interface wraps a function. Three core arguments: fn, inputs, outputs.

2 · Load and split the PDF

def document_loader(file):
    # Colab fix: gr.File(type="filepath") passes a str path, older Gradio passed an object with .name
    loader = PyPDFLoader(file if isinstance(file, str) else file.name)
    loaded_document = loader.load()
    return loaded_document

def text_splitter(data):
    text_splitter = RecursiveCharacterTextSplitter(
        chunk_size=1000,
        chunk_overlap=50,
        length_function=len,
    )
    chunks = text_splitter.split_documents(data)
    return chunks

PyPDFLoader returns one Document per page. RecursiveCharacterTextSplitter tries big separators first (paragraphs), then smaller ones, so chunks stay ≤ 1000 characters; 50 characters of overlap keep sentences that cross a boundary.

3 · Embeddings and the vector database

def vector_database(chunks):
    embedding_model = watsonx_embedding()
    # Colab fix: own collection per call — without collection_name every call appends to Chroma's shared
    # in-memory 'langchain' collection, so chunks pile up and come back duplicated
    vectordb = Chroma.from_documents(chunks, embedding_model, collection_name=f"qabot_{uuid.uuid4().hex[:8]}")
    return vectordb

def watsonx_embedding():
    # Colab (Gemini): ibm/slate-125m-english-rtrvr-v2 → models/gemini-embedding-2
    # (the function name is kept so the lab's screenshot tasks still match)
    watsonx_embedding = GoogleGenerativeAIEmbeddings(model="models/gemini-embedding-2")
    return watsonx_embedding

4 · Retriever and QA chain

def retriever(file):
    splits = document_loader(file)
    chunks = text_splitter(splits)
    vectordb = vector_database(chunks)
    retriever = vectordb.as_retriever()
    return retriever

def retriever_qa(file, query):
    llm = get_llm()
    retriever_obj = retriever(file)
    qa = RetrievalQA.from_chain_type(llm=llm,
                                    chain_type="stuff",
                                    retriever=retriever_obj,
                                    return_source_documents=False)
    response = qa.invoke(query)
    return response['result']

🔍 Deeper look: how chunk_size and chunk_overlap really work

How the recursive splitter decides. RecursiveCharacterTextSplitter has a list of separators, from big to small: ["\n\n", "\n", " ", ""] (paragraph, line, word, character). It first cuts at paragraphs. Any piece still longer than chunk_size is cut again at lines, then at words. Small pieces are then joined back together until a chunk is almost chunk_size long. Result: chunks end at natural boundaries whenever possible.

What overlap does. With chunk_overlap=50 the last ~50 characters of one chunk are repeated at the start of the next. A sentence that crosses the border is then complete in at least one chunk:

ChunkText (overlap in bold)
3…Employees may use personal phones for work. Lost phones must be reported
4Lost phones must be reported to IT within 24 hours. Remote wipe may be used…

Without overlap, chunk 3 would end with a half rule and chunk 4 would start with "to IT within 24 hours" — neither chunk answers "What do I do if I lose my phone?" well.

Characters vs tokens. LangChain's splitters count characters; LlamaIndex's SentenceSplitter counts tokens. In English, 1 token ≈ 4 characters ≈ ¾ word (the reading: 100 tokens ≈ 75 words). So chunk_size=1000 in LangChain (~250 tokens) is about four times smaller than chunk_size=1024 in LlamaIndex (~4,000 characters). Keep this in mind when you copy settings between frameworks.

def create_watsonx_embedding() -> GoogleGenAIEmbedding:

def create_watsonx_llm(
    temperature: float = config.TEMPERATURE,
    max_new_tokens: int = config.MAX_NEW_TOKENS,
    decoding_method: str = "sample"
) -> GoogleGenAI:
    if decoding_method == "greedy":
        temperature = 0.0
    max_out = max(max_new_tokens, 1024)          # Gemini counts thinking tokens in max_output_tokens
    if config.LLM_MODEL_ID.startswith("gemini-3"):
        # Gemini 3: Google recommends the default temperature (1.0); low values can cause looping.
        # thinking_level="low" leaves the token budget for the answer.
        gen_config = types.GenerateContentConfig(
            max_output_tokens=max_out,
            thinking_config=types.ThinkingConfig(thinking_level="low"),
        )
    else:
        # Gemini 2.5: temperature is fine; cap thinking with a budget
        gen_config = types.GenerateContentConfig(
            temperature=temperature,
            max_output_tokens=max_out,
            thinking_config=types.ThinkingConfig(thinking_budget=512),
        )
    llm = GoogleGenAI(
        model=config.LLM_MODEL_ID,
        max_tokens=max_out,
        generation_config=gen_config,   # with generation_config, the temperature/max_tokens args are not sent
    )
    logger.info(f"Created LLM: {config.LLM_MODEL_ID}")
    return llm

📝 Graded Quiz: Build RAG Apps with LlamaIndex

Q1. In the context of Retrieval-Augmented Generation (RAG), which step does LlamaIndex combine with the prompt augmentation process?

✅ Answer B. LlamaIndex combines prompt augmentation with LLM response generation, especially when using a response synthesizer.

Q2. What is the purpose of LlamaIndex's `LangChainNodeParser`?

✅ Answer C. LlamaIndex's `LangChainNodeParser` wraps around LangChain's text splitters, allowing their use within LlamaIndex.

Q3. What is the main purpose of embedding the user's original prompt in LlamaIndex?

✅ Answer B. Embedding the user's original prompt is typically done to retrieve relevant chunks from the vector store, ensuring the embedding model matches the one used for chunk embeddings. The same embedding model as the index must be used.

Q4. Which LangChain splitter is most similar to LlamaIndex’s `SentenceSplitter`?

✅ Answer D. LlamaIndex’s `SentenceSplitter`recursively splits text based on predefined characters. By default, `SentenceSplitter` splits text by paragraphs, where paragraphs are identified by multiple newline characters in succession. If some of the resulting chunks are still too large, those chunks get split using secondary splitters, such as periods and commas. In spirit this is most similar to LangChain’s Both split recursively on predefined characters (paragraphs first, then smaller units).

Q5. What is the purpose of LlamaIndex's “prompt synthesizer”?

✅ Answer C. The “prompt synthesizer” in LlamaIndex takes the user’s original prompt and retrieved nodes as inputs, performs prompt augmentation internally, and passes the augmented prompt to the LLM.

Q6. What is a key feature of LlamaIndex's `VectorStoreIndex`?

✅ Answer A. LlamaIndex's `VectorStoreIndex` wraps external vector databases into a native class, making downstream code agnostic to the vector store backend.

Q7. Anna wants to develop a RAG system with minimal reliance on external libraries. She prefers a framework with robust internal capabilities for tasks like document loading and in-memory vector storage, while still allowing integration with external libraries and services when needed. Which framework, LangChain or LlamaIndex, best suits Anna's needs, and why?

✅ Answer A. LlamaIndex has superior native tools than LangChain for most tasks but still allows numerous integrations with external libraries. LangChain, on the other hand, tends to rely more on external integrations. This does not imply that one framework is better overall; rather, they are different approaches taken by different projects. However, if one’s objective was to minimize reliance on external libraries, LlamaIndex would be the correct choice because more functionality is built into LlamaIndex’s core library.

from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_chroma import Chroma
from langchain_community.document_loaders import PyPDFLoader
import uuid

def document_loader(file):
    loader = PyPDFLoader(file if isinstance(file, str) else file.name)   # str path from gr.File(type="filepath")
    return loader.load()                     # one Document per page, metadata has 'source' and 'page' (0-based)

def text_splitter(data):
    text_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=50, length_function=len)
    return text_splitter.split_documents(data)

def watsonx_embedding():                     # name kept from the lab
    return GoogleGenerativeAIEmbeddings(model="models/gemini-embedding-2")

def vector_database(chunks):
    # own collection per call — otherwise every call appends to Chroma's shared 'langchain' collection
    return Chroma.from_documents(chunks, watsonx_embedding(), collection_name=f"qabot_{uuid.uuid4().hex[:8]}")

  • Renaming the placeholders (e.g. {docs}) — RetrievalQA's stuff chain fills only {context} and {question}.

  • In LlamaIndex the same idea uses {context_str} and {query_str}.

from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

def _text(content):                            # Gradio 6 may send content as a list of parts
    if isinstance(content, list):
        return " ".join(p.get("text", "") if isinstance(p, dict) else str(p) for p in content)
    return str(content)

def chat(message, history):
    msgs = [SystemMessage("You are a concise, friendly assistant.")]
    for turn in history:                       # "messages" format: {"role", "content"}

    msgs.append(HumanMessage(_text(message)))
    return llm.invoke(msgs).text

def words_cut(chunks, docs):
    n = 0
    for c in chunks:
        t = docs[c.metadata["page"] - 1].page_content; i = t.find(c.page_content); j = i + len(c.page_content)

One-page cheat sheet

RAG in one line

Retrieve relevant chunks → add them to the prompt → LLM answers. No retraining. Retriever + Generator. 4 steps: text embedding, retrieval, augmented query creation, model generation.

Encoding

Prompt vector = average of token embeddings. Documents → chunks → context encoder → vectors in the knowledge base / vector DB.

Similarity

Dot product Σqᵢcᵢ (magnitude + direction) · cosine q·c/(|q||c|) (direction) · top-K = argsort, K=3.

Why not long context?

128k tokens ≈ 96,000 words; limits: input dependency, limited capacity, redundancy (needle in haystack), processing time, cost.
